# ADR 0005: 许可选择——Apache-2.0 与 DCO

## 背景

仓库根 `LICENSE` 是 Apache License 2.0 全文，README 的「许可与数据归属」一节也写明
「含专利授权条款，云厂商友好」，CONTRIBUTING 要求每个 commit 带 `Signed-off-by`
（DCO），不签 CLA。但仓库里没有任何一份文档解释过**为什么**是这套组合：

1. 引擎要被硬件厂商（PAL 后端）、云厂商（推理运行时）、内容工具链嵌进去，
   对方第一件事是过法务；
2. 具身仿真面会长期沉淀数据集与评测协议，这些资产的法律地位与引擎代码不同；
3. 项目没有商业实体做版权集中，也没有钱养法务流程。

## 决策

1. **引擎代码用 Apache-2.0**，不做双许可、不换 copyleft。
2. **贡献用 DCO**（`Signed-off-by`），不要求 CLA、不做版权转让。
3. **代码许可不管数据**：用户导入的 URDF、采集的数据集、训练与评测产物归用户所有
   （README「你的数据 100% 归你」）；第三方美术资产一律 CC0，来源逐项登记。
4. **License 变更属 BDFL 保留事项**，必须公开说明理由（GOVERNANCE.md）。

## 为什么不是 MIT

MIT 全文不提专利。对一家要评估「把引擎嵌进自家 SDK」的芯片或云厂商，法务会追问：
贡献者的专利怎么处理？MIT 的回答是「没写，你们自己谈」——于是每个贡献者都要单独
签一份专利许可，谈不动也留不下记录。

Apache-2.0 §3 一次解决：贡献即授予专利许可，且带专利报复条款（谁就本项目专利起诉，
许可自动终止）。这正是「云厂商友好」四个字的实际含义，也是 README 敢这么写的依据。

## 为什么不是 AGPL

AGPL 的第 13 条把「通过网络提供服务」也算作分发。引擎的典型用法恰好是嵌进闭源外壳
（`platforms/*`、商业编辑器、硬件 SDK）再对外提供服务——选 AGPL 等于要求这些外壳
整条开源，直接把最可能买单的合作方挡在门外。

项目也不靠 license 收费：护城河是评测协议、数据集与标准，不是授权条款。用 copyleft
去锁一个还没形成生态的引擎，锁住的是自己。

## 为什么不做双许可（AGPL + 商业授权）

双许可的前提是**版权集中**：所有贡献都得签 CLA 把版权（或至少再许可权）让给项目主体，
否则项目方无权另行授权。这与「外部贡献者平权、Hacktoberfest 级的一次性 PR 也能进」
直接冲突，还要维护两套授权文本与谈判流程。早期阶段不值得。

若将来真要走这条路，必须先反转本 ADR 第 2 条（改回 CLA），所以那会是一次显式的、
需要新 ADR 的决策，而不是悄悄加一页商业授权。

## 为什么 DCO 而不是 CLA

CLA 是合同：个人要签、公司要审批、一次贡献要走一遍流程。对一次性贡献者，这一步的
流失率高得离谱；对实习生/学生贡献者，他们往往无权签。DCO 只要 commit 里一行
`Signed-off-by: Name <email>`，声明「我有权提交这段代码」——法律效果对本项目够用，
流程成本为零（CONTRIBUTING 第 41 行）。

代价是项目不获得额外的再许可权（见上一节），这是有意接受的：换来的是贡献门槛。

## 后果

- ✅ 商用路径清晰：闭源外壳可以嵌引擎，专利许可随代码到达，不需要逐个谈判。
- ✅ 贡献门槛低：DCO 一行，学生与一次性贡献者都能进。
- ✅ 数据与代码分家：用户的 URDF/数据集/模型不被引擎许可牵连。
- ⚠️ 没有 copyleft：有人可以拿引擎做闭源产品而不回馈。缓解手段是生态（标准、
  评测协议、数据）而不是条款——这条是选择 Apache-2.0 时就知道要付的代价。
- ⚠️ **商标不在授权范围内**（Apache-2.0 §6 明确不授予商标权）。「OriEra」名称与
  logo 的使用政策目前**尚未单独成文**，这是已知缺口：外部产品宣称「基于 OriEra」
  时没有可引用的规则。补一份 `TRADEMARK.md` 是后续动作。
- ⚠️ 数据集许可尚未统一：仓库内 CC0 是美术资产的口径，具身评测集若要对外发布，
  需要单独的数据许可（不在本 ADR 范围内，留待数据集发布时决定）。

## 什么情况下会重新考虑

1. **可持续性受威胁**：若闭源商用普遍且完全不回馈，导致维护不可持续，优先考虑的
   是 open-core（引擎保持 Apache-2.0，评测/数据服务商业化），而不是改引擎许可。
2. **上游许可冲突**：若必须引入 GPL 系组件，正确做法是移除该依赖或做进程隔离，
   **不是**把本项目改成 GPL。
3. **社区明确要求 copyleft 保护**：可对特定子项目（例如某些数据集工具）单独采用
   copyleft，而不是全仓切换。
4. **建立版权集中**：只有决定走双许可时才需要 CLA，那必然伴随一次治理变更。

以上任一情形都按 GOVERNANCE.md 的「改 License」流程：BDFL 决定 + 公开理由 + 新 ADR。
