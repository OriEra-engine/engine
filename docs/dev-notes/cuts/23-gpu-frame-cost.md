# 第23刀 · 渲染层帧成本基准

> **工作记录（2026-11）。** 文中"本机/开发机"指当时跑基准的那台没有 GPU 的机器（llvmpipe 软件光栅化），毫秒数不是 GPU 帧时间，只作同机回归。文中的"补丁"是当时的交付方式，对应关系见[索引](../README.md)。

补丁 **023**。基于 `0387718`（v0.13.0），**只依赖基线**——001–022 都没碰 `oriera-render`，可独立 apply。纯基准，零生产代码改动。

---

## 一、先说结论：这一刀量出来的不是 GPU 帧时间

**本机没有真 GPU。** `/dev/dri` 不存在、没有 Vulkan ICD，wgpu 只能走 mesa 的 llvmpipe（软件光栅化，`device_type=Cpu`）。下面所有毫秒数都是 CPU 模拟出来的，**不能当 GPU 帧时间引用，也不能外推到真卡**，只作同机回归。

但有三条结论不依赖具体数字，是结构性的，换真卡也成立：

1. **每个绘制单元的成本与分辨率无关**（966×544 与 1920×1080 下都是 35–38 µs）。这说明它花在 CPU 侧，不是光栅化。
2. **固定底噪占大头**：544p 下画 1 个铺满屏幕的方块要 8 ms，其中约 7 ms 与画什么无关。
3. **两条都来自同一个设计**：`render_scene_views` 是快照式接口，每帧重建一切、每次都回读。做实时 demo 之前必须换路径，否则画面再简单也跑不动。

## 二、测了什么

`crates/oriera-render/benches/gpu_frame.rs`，两根轴分开测，避免把"画得多"和"画得满"混在一起：

| 轴 | 场景 | 增长的是 |
|---|---|---|
| `draw/n` | n 个方块平铺铺满视口，互不遮挡 | 绘制数、顶点上传、bind group 构造 |
| `fill/n` | n 个方块全叠在同一位置，铺满视口 | overdraw 倍数（片元着色、深度测试） |

两根轴的覆盖率都约 86%，像素量恒定，所以轴上唯一的变量就是名字里那个。分辨率两档：966×544（对标演示画面的分辨率）和 1920×1080。

```bash
WGPU_BACKEND=gl EGL_PLATFORM=surfaceless \
  cargo bench -p oriera-render --features render-wgpu --bench gpu_frame -- --nocapture breakdown
```

## 三、读数（llvmpipe，中位数，15+10 次采样）

| 场景 | parts | µs/帧 | 占 60fps 预算 | 相对上一档的边际 | 覆盖率 |
|---|---:|---:|---:|---:|---:|
| draw/966×544 | 1 | 8008 | 48.0% | — | 86.5% |
| draw/966×544 | 64 | 12904 | 77.4% | 77.7 µs/单位 | 83.1% |
| draw/966×544 | 512 | 28177 | 169.1% | **34.1 µs/单位** | 90.5% |
| draw/966×544 | 2048 | 82049 | 492.3% | **35.1 µs/单位** | 93.5% |
| fill/966×544 | 4 | 10927 | 65.6% | — | 86.5% |
| fill/966×544 | 16 | 24075 | 144.4% | **1096 µs/倍** | 86.5% |
| fill/966×544 | 64 | 81168 | 487.0% | **1189 µs/倍** | 86.5% |
| draw/1920×1080 | 1 | 32768 | 196.6% | — | 86.5% |
| draw/1920×1080 | 64 | 43717 | 262.3% | 173.8 µs/单位 | 83.1% |
| draw/1920×1080 | 512 | 74586 | 447.5% | 68.9 µs/单位 | 90.3% |
| draw/1920×1080 | 2048 | 132886 | 797.3% | **38.0 µs/单位** | 93.1% |
| fill/1920×1080 | 4 | 58924 | 353.5% | — | 86.5% |
| fill/1920×1080 | 16 | 104638 | 627.8% | **3810 µs/倍** | 86.5% |
| fill/1920×1080 | 64 | 324087 | 1944.5% | **4572 µs/倍** | 86.5% |

**哪些数能信、哪些不能：**

- **512–2048 档稳定**，三次运行离散 ±2%：每绘制单元 34–38 µs（544p）、38–69 µs（1080p）。
- **1–64 档在噪声内**，三次运行差到 ±30%（draw/1 在 1080p 下量到过 32.8 / 47.9 / 49.2 ms）。这一档不该用来下结论。
- overdraw 成本与像素数成正比：544p 约 1.1–1.2 ms/倍，1080p 约 3.8–4.6 ms/倍，换算下来都是每像素 2–2.5 ns，两档一致。

## 四、三条结构性结论的依据

### 4.1 每绘制单元的成本在 CPU 侧

512→2048 这一段，两个分辨率差 3.9 倍像素，边际却都是 35–38 µs。如果是光栅化成本，1080p 应该显著更贵。没更贵，说明这部分时间花在提交侧：

`render_scene_views(&self, parts: &[ScenePart], camera)` 每次调用，对**每个 part** 新建顶点缓冲、新建 bind group，再 draw。n 个物件 = n 次缓冲分配 + n 次 bind group 构造。这是按"渲染一张快照"设计的，不是按"每帧 60 次渲染一座城"设计的。

### 4.2 固定底噪占大头

544p 下画 1 个方块 8.0 ms，减去 1 倍 overdraw（约 1.1 ms），剩约 **6.9 ms 与场景内容无关**。这部分是每帧新建颜色/深度纹理、清屏、`map_async` 回读到 `Vec<u8>`。1080p 下这一项 33–49 ms。

**这个数无法单独量**：公开接口拒收空场景（`Device("empty scene or zero-sized target")`），也没有开关能关掉回读。6.9 ms 是"1 个方块减 1 倍 overdraw"估出来的，不是直接测量。

### 4.3 对整机 1.3% 的修正

第14刀的整机帧成本（137–262 µs）**不含渲染**。把渲染按现在的接口加进去，哪怕在软件光栅化下也直接超预算几个数量级。所以之前"整机非常宽裕"这句话的准确表述是：**模拟与推理段宽裕，渲染段尚未进入帧循环，且现有接口不适合进入。**

## 五、这对路线二意味着什么

路线二的前提是"画面简单、行为难"。这一刀确认了：**画面简单救不了接口设计**。低多边形城市仍然是上千个物件，按每物件一次缓冲分配的做法，在真卡上也大概率卡在 CPU 提交侧——具体多少微秒不知道，需要真卡重跑，但"每物件每帧分配"这个模式本身就该改。

呈现层最小闭环的顺序因此调整为：

1. **持久渲染路径**（新增，additive）：网格上传一次并缓存，按 mesh 身份复用缓冲；同类物件走实例化；颜色/深度目标持久化；默认不回读。现有快照接口原样保留给离线出图和测试。
2. **窗口 + 交换链**：在第 1 步之上接，否则一接上去就是在慢路径上做优化。
3. 低多边形场景、NavMesh、动画状态机——不变。

第 1 步新增公开面，按仓库纪律要走 RFC（≥7 天评论）。它不碰 #13 步 C/D，也不碰任何生产调用路径。

## 六、还缺什么

| 缺口 | 影响 | 怎么补 |
|---|---|---|
| **没有真 GPU 读数** | 所有毫秒数不可对外、不可外推 | 一台有 `/dev/dri` 的机器，`WGPU_BACKEND=vulkan` 跑同一条命令，bench 自动打印适配器名 |
| 无法单独量底噪 | 固定成本只能估 | 第 1 步的持久路径落地后，回读可关，自然分开 |
| 低档位噪声大 | 1–64 档不可用 | 无需处理；真卡上这一档才有意义 |
| 无阴影 / IBL / 后处理的基准 | 这些功能本身还没有 | 功能落地时再加轴，现在加是空测 |

## 八、踩过的坑

- 环境变量是 `WGPU_BACKEND`（不是 `ORIERA_*`），且需要 `EGL_PLATFORM=surfaceless`；默认 PRIMARY 后端报 "no usable adapter"。
- wgpu 30：`InstanceDescriptor` 无 `Default`；`initialize_adapter_from_env_or_default` 返回 `Result` 而非 `Option`。
- 第一版场景方块太小（覆盖率 0–6%），fill 轴实际没在测填充——draw 与 fill 读数几乎一样就是信号。改成网格铺满视口后两轴才分开。
- 全屏 overdraw 在软件光栅化下每倍 1–4 ms，fill 轴档位必须压到 64 以内，否则一轮 bench 跑不完。
- 输出里必须有适配器名和设备类型；`device_type=Cpu` 时 bench 自己打印"不是 GPU 帧时间"。
