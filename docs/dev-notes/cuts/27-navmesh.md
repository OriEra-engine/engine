## 一句话

给 NPC 一条能复现的路线：凸多边形导航网格（邻接从共享边自动推导）→ A* 走多边形图 → 漏斗算法拉直 → `NavAgentSystem` 沿路走。全是 CPU，`path_fingerprint` 供 episode 回执用。

## 一、为什么做这个

路线二列了四件事：呈现层最小闭环（窗口+交换链，要真卡且要单独评审）、低多边形场景、**NavMesh + 简单动画状态机**、TTS/ASR 外部接入。第三项纯 CPU，不需要真卡。

这一刀只做 **NavMesh**，动画状态机留到下一刀（补丁 028）。理由是两者没有代码耦合：导航决定"往哪走"，动画决定"走起来长什么样"，分开评审更清楚。

## 二、做了什么

| 接口 | 行为 |
|---|---|
| `NavMesh::from_polygons(&[Vec<[f32;2]>])` | 建网格。绕向自动规整为正面积方向，首尾闭合点与沿途重复点丢掉；顶点 <3、面积塌陷、非凸、共享边匹配不唯一，四种都在构建期报 `NavError` |
| `poly_count` / `poly` / `centroid` / `neighbors` | 只读查询；邻接表按多边形下标排序，不依赖任何哈希顺序 |
| `locate(p)` | 点在哪块面片上（含边界）；边界点归属下标最小的那个，保证可复现 |
| `project(p)` | 任意点贴到网格最近点（点已在网格内则原样返回） |
| `find_path(from, to)` | A* 走多边形图（边权=质心间距，启发=质心到目标质心的直线距离），再用漏斗拉直；起终点越界先投影，同一面片直接直线，不可达返回 `None` |
| `segment_walkable(a, b)` | 线段是否整段可行，0.25 单位步长采样（近似，明说不当解析谓词） |
| `NavAgent` | `go_to` / `halt` / `speed` / `arrived` / `unreachable` / `path` / `cursor` / `repaths` |
| `NavAgentSystem` | 运动学移动器：自己写 `Position`，把本帧真实位移折算成 `Velocity` 写回；位移预算 = `speed * dt_eff`，可跨多个路点；节奏跟 `TimeScale` |
| `path_fingerprint(path)` | FNV-1a 64，覆盖点数与坐标位模式，同输入同值 |

两个值得单说的设计决定：

**邻接不靠额外输入。** 只要求"两个多边形共享一条边、端点顺序相反"，整条边重合才算邻接——半条边重合是建模错误，不是邻接。检测是 O(E²) 两两比边，几百个面片够用，城市级要换空间索引（已写进 STABILITY 边界）。

**左右侧定向只在一个地方定死。** 漏斗的两个收窄条件对 left/right 不是对称的，符号翻一次就会把路线拉直成穿墙直线。第一次实现就把符号搞反了——测试里 `every_leg_of_the_path_is_walkable` 立刻抓到"这段穿出了网格"，拐点也消失了。现在符号来源写在 `route()` 里，由那条测试钉住。

## 四、诚实边界

- 多边形**必须凸**。非凸在构建期被拒，不是悄悄切角。
- 2D 平面（`Position` 的 `x`/`y`，`y` 向下，与物理一致），没有高度、没有层间连接——楼梯/电梯要做成额外面片加手工接边，本步不做。
- 没有动态障碍、没有群体避让。要避让写在上层（改 `Velocity` / 改目标），导航只管路线。
- `NavAgentSystem` **不能和物理积分器同时驱动同一批实体**：两个写者会互相覆盖。这条没有协商机制，写在文档头与 STABILITY 里。
- 路线好坏没有基准：本步只保证"最短走廊 + 可复现"，没有做路径长度与规划耗时的对比度量。等低多边形场景落地后再补基准更有意义。
- 城市级规模未验证：O(E²) 邻接检测在几十个面片上是微秒级，几百个也还行，上千面片就该爆了。
