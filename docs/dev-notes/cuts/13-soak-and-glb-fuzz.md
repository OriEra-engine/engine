## 一、为什么补这两块

此前测试体系有两层：单测钉"一次操作对不对"，criterion 基准钉"一次操作多快"。缺的是第三类和第四类问题：

| 缺口 | 谁来补 | 典型漏网 |
|---|---|---|
| **跑久了会不会坏** | 016 soak | 台账/记忆无界增长、累积浮点漂移、分配器卡在挤压态 |
| **坏输入会不会炸** | 017 GLB fuzz | 外部生成资产的畸形字节导致 panic 或越界读 |

GLB 那块尤其要紧：解码器是引擎面向 Tripo / Rodin / Hyper3D 的**第一道字节边界**，输入完全不可信。

## 二、补丁 016 · 长跑 soak（9 条）

文件 `crates/oriera-agent/tests/soak.rs`，328 行。放 agent crate 是因为它同时依赖 core / infer / subsys，能跨层跑。

### 规模可调，默认进 CI

默认 2000 圈，debug 下 **0.02s** 跑完，**不加 `#[ignore]`**——每次 `cargo test` 都跑。想压更久：

```sh
ORIERA_SOAK_ROUNDS=20000 cargo test -p oriera-agent --test soak -- --nocapture
```

实测 20000 圈 **0.14s**，同样全通。

这不是"跑一夜"的老式 soak，是**确定性长跑**：语料由帧号/回合号直接算出，无随机源，失败可精确复现。

### 三组断言

**记忆有界性与无漂移**（3 条）
- 容量 64，灌 N 条后 `len_total()` 全程 ≤ 64 且最终恰好饱和在 64（不只查上界，也查没被过度淘汰）；
- 同序列跑两遍，最终召回逐条相等（turn / text / importance）；
- 双 agent 各 32，互不挤占，两边都还能召回。

**路由台账有界性与长跑双跑**（2 条）
- 云端行按 `i % 3` 在 Closed / Open 间交替，**降级路径也被长跑覆盖**；台账全程 ≤ 256 且最终饱和；
- 同序列两遍，整本台账 `matches()` 逐条相等。

**帧循环与分配器无病态**（4 条）
- 长跑下计时表长度恒定、`avg_frame_ms()` 始终有限非负（不被累积成 NaN / Inf）；
- **持续超载 N 圈 → 恢复正常 N 圈**，节流必须回弹（`relaxed >= squeezed`），不得卡死在挤压态；
- 分配器 `off()` 时长跑下节流恒为 1.0，无残留；
- 帧号与时间戳单调不倒退。

### 结果

**9 条全通，未发现问题。** 这是有价值的阴性结论：容量闸、台账环形截断、分配器回弹机制在长跑下都成立。

## 三、补丁 017 · GLB 属性测试 + 确定性 fuzz（13 条）

文件 `crates/oriera-asset/tests/glb_properties.rs`，460 行。

### 不引 proptest / rand

语料由内置 **xorshift64\*** 生成，种子写死源码（`0x0A1E_0001`…`0004`），纯整数运算跨平台逐位一致。**不给仓库添依赖**，且 CI 上每次跑同一批语料——红了就是真回归，不是"这次运气不好"。

### 两条核心不变量

**1. 绝不 panic**（4 条 fuzz）
- 2000 例纯随机字节（长度 0–512）；
- 2000 例**带合法 glTF 头**的随机字节——逼解码器走进容器解析之后的分支，而不是第一道魔数检查就挡回；
- 4000 例合法文件单字节变异；
- **每个字节位置各翻一次最高位**，系统扫过容器头 / JSON 文本 / BIN 浮点三类区域。

**2. 凡 `Ok`，输出必然自洽**（`assert_mesh_invariants`）
- 坐标全有限；
- 索引不越顶点界；
- 法线数量与顶点数对齐、分量有限；
- **包围盒与坐标实算逐轴一致**（渲染端归一化直接吃它）；
- 基础色分量有限。

### 防空转断言（这条值得单说）

fuzz 测试有个隐蔽陷阱：**若变异后全被拒，`if let Ok(...)` 里的不变量断言一次都没跑过，测试是绿的假象**。

所以两条变异 fuzz 各加了存活计数断言：单字节变异要求 `accepted > 100`，逐位翻转要求 `accepted > 0`。实测均通过——BIN 区浮点字节变异大量存活，不变量检查确实执行了。

### 另外五组

- **任意前缀截断必拒**：遍历合法文件的每一个切点，全部必须 `Err`，且错误类型限于 `NotGlb | Truncated`（半下载文件应在容器层挡住，不该走到几何解析）；
- **双跑逐位一致**：固定网格 + 200 例随机合法网格，坐标 roundtrip 逐位相等；
- **非有限坐标必拒**：NaN / +Inf / -Inf 三种，均须 `NonFinitePosition`；
- **索引越界必拒**：手造 3 顶点 / 索引含 3，须 `IndexOutOfRange { index: 3, vertices: 3 }`；
- **声明长度溢出不得越读**：JSON chunk 长度字段填 `u32::MAX` 等，必须拒；尾巴追加垃圾 → `NotGlb`（总长不符，不静默忽略）。

### 结果

**13 条全通，未抓到 bug。** 与 015 那次不同——这次是干净的阴性结论：解码器的 fail-closed 纪律在字节层面是成立的，`NonFinitePosition` / `IndexOutOfRange` / `OutOfBounds` 这些显式拒绝分支不是摆设。

诚实说一句：fuzz 没找到问题**不等于没有问题的证明**，只等于这批语料没找到。语料种子与规模都写在源码里，后续想扩规模或换种子都是改一个常量的事。

## 五、边界

- **零生产代码改动**。两个文件都在 `tests/` 下，不进任何 crate 的 lib 或 bin。
- **不触发跨层审批**。纯测试设施，与步 C 的审批流程无关。
- **soak 不测真实时间**。跑的是确定性圈数，不是墙钟意义上的"跑一夜"；真实长时运行的内存曲线需要另接进程级观测，本轮未做。
- **fuzz 不覆盖 scene / rig 解码路径**。只打 `decode_glb_mesh`（L8 闸口用的那条）；`decode_glb_scene` / `decode_glb_rig` 不在本轮范围。
- **S2 死线仍然有效**，本刀不构成任何"已接线"。
