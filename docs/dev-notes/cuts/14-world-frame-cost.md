# 第14刀 · 整机帧成本（整机油耗）

> **工作记录（2026-11）。** 文中"本机/开发机"指当时跑基准的那台没有 GPU 的机器（llvmpipe 软件光栅化），毫秒数不是 GPU 帧时间，只作同机回归。文中的"补丁"是当时的交付方式，对应关系见[索引](../README.md)。

补丁 **018**。基于 `0387718`（v0.13.0），顺序叠在 001–017 之后。纯基准，零生产代码改动。

---

## 一、先说结论：预判错了

上一轮的判断是"零件都便宜，装到一起可能就超预算"。**实测推翻了这个预判。**

一个物理 + 记忆 + 推理 + 资产闸口全开的世界，一帧 **约 190–260 µs，占 60fps 预算的 1.1–1.6%**。整机在当前规模下**非常宽裕**，帧预算根本不是瓶颈。

但这一刀真正的收获不是"没超预算"，是**找到了真正会撑不住的那个点**，以及**修正了一个被高估的读数**。

---

## 二、整机分解

`cargo bench -p oriera-agent --features rigid3d --bench world_frame -- --nocapture breakdown`

一帧四段：L6 物理（关节链 + n 个自由刚体）、L9 记忆检索、L7 推理提交 + 收割、L8 资产闸口。

| 规模 | physics | memory | infer | gate | 合计 | 占预算 |
|---|---|---|---|---|---|---|
| p4 / m60 | 68.8 | 35.0 | 25.9 | 7.8 | **137.5 µs** | 0.8% |
| p16 / m120 | 82.4 | 70.0 | 27.6 | 7.0 | **187.1 µs** | 1.1% |
| p16 / m240 | 86.1 | 134.5 | 33.3 | 8.1 | **262.0 µs** | 1.6% |

（中位数，µs；帧预算 16667 µs。三次独立运行，physics / memory / gate 三段离散度 ±3%。）

### criterion 差值法：同口径边际成本

同一夹具（p16 / m120）分别关掉某一段，差值才是该段的真实边际成本：

| 变体 | 耗时 | 该段边际 |
|---|---|---|
| full | 209.4 µs | — |
| no_physics | 111.2 µs | **physics ≈ 98 µs** |
| no_memory | 119.3 µs | **memory ≈ 90 µs** |
| no_infer | 158.6 µs | **infer ≈ 51 µs** |
| no_gate | 201.3 µs | **gate ≈ 8 µs** |
| idle_baseline | 2.2 ns | 夹具开销可忽略 |

**注意：四段边际之和（247 µs）大于整机（209 µs）。** 这不是测量错误——去掉一段同时也去掉了它与其它段的缓存/调度争抢，边际成本不可简单相加。这也正是要用差值法而不是把孤立基准的数字加起来的原因。

## 三、真正的发现：记忆检索的规模悬崖

检索是全量扫描，成本线性于窗口。小窗口下它便宜，于是此前一直没被当回事。把窗口放大：

| 记忆条数 | retrieve 中位 | 占 60fps 预算 |
|---|---|---|
| 240 | 140 µs | 0.84% |
| 1 000 | 594 µs | 3.6% |
| 5 000 | 2 950 µs | **17.7%** |
| 20 000 | 11 667 µs | **70.0%** |
| 50 000 | 29 715 µs | **178%** ← 单次检索已超整帧预算 |

约 **0.58 µs/条**，干净的线性。

**这就是"记忆检索全量扫描该不该改"的定标答案**，不再是凭感觉：

- **≤1 000 条**：不用改，占比个位数；
- **5 000 条**：吃掉近 18% 预算，必须限频或移出帧；
- **20 000 条**：70% 预算，其它什么都别干了，必须改；
- **50 000 条**：单次检索就超帧，当前架构不成立。

所以决策依赖一个尚未确定的输入：**目标场景的记忆规模到底多大**。具身训练每环境的记忆可能不大，但长期陪伴 / 世界历史会很大。这个数定了，改不改、什么时候改就定了。

## 四、修正一个被高估的读数

此前性能矩阵记的 `InferJobs` 是 **~45 µs/job**，据此建议 Realtime deadline 下限 ≥1 ms。

整机里实测只有 **23–35 µs**，差了近一倍。查了原因：

- 孤立基准用 `iter_batched` **每轮新建 `InferJobs`**；整机里池是长期复用的。
- 做了对照实验：复用池 21.8–32.0 µs vs 每轮新建 23.1–33.9 µs——**两者几乎相同，池构造不是原因**。
- 真实原因是**该项本身方差极大**：三次运行 n=1 分别测到 35.1 / 30.5 / 23.6 µs，波动约 1.5 倍。线程 spawn 受 OS 调度支配，不是一个稳定常数。

**结论要修正两处**：

1. "~45 µs/job"应改为**"20–50 µs，高方差"**，不能当稳态常数用；
2. 线程池改造的收益**不是省 CPU**（整机里才 51 µs，占 0.3%），而是**降方差**。对 Realtime 槽位来说，不可预测比慢更致命——deadline 要按最坏情况留余量，而不是按中位数。

deadline ≥1 ms 的建议**仍然成立**，但依据从"覆盖 45 µs 均值"变成"覆盖高方差尾部"。

### 并发放大

| 一帧内提交 n 个 job | 中位 | 每 job |
|---|---|---|
| 1 | 23.2 µs | 23.2 |
| 4 | 74.9 µs | 18.7 |
| 8 | 139.3 µs | 17.4 |
| 16 | 286.5 µs | 17.9 |

每 job 成本随并发略降（spawn 开销部分重叠），但总量线性增长。**16 并发 = 286 µs，仍只占 1.7% 预算**——所以"一 job 一线程"在当前并发下也不是吞吐问题。

## 五、这一刀改变了什么优先级

据此修正上一轮给的建议：

| 上轮判断 | 实测后修正 |
|---|---|
| 整机可能超帧预算 | **错**。当前规模 1.1–1.6%，很宽裕 |
| 线程池改造省 CPU | **收益主要是降方差**，不是吞吐；优先级应下调 |
| 记忆全量扫描待立项 | **确认是真问题，但触发条件明确了**：≥5 000 条才值得动 |
| 先定标再决定改不改 | **成立**，且现在缺的输入收敛成一个数：目标记忆规模 |

**下一步该问的不是"改哪个模块"，而是"目标场景要多少条记忆、多少并发环境"。** 这两个数一定，架构改造的优先级自动排出来。

## 六、方法与诚实边界

- **段间用 `Instant` 逐段实测**，不估算；criterion 负责统计稳定性与差值法。
- **infer 段完整计入 submit + drain**，不做摊销假设。drain 循环后补一次 `poll` 收尾（worker 先 `send` 再减 `inflight`）。
- **整机段读数与孤立基准口径不同**：这里世界持续演进（prop 会落定、接触状态变化），且含 `Instant` 计时开销。**不能拿整机的 physics 82 µs 去减孤立基准的 53 µs 得出"多花了 29 µs"**——那是错误比较。同口径比较只在差值组内部做。
- **方差已披露**：infer 段波动约 1.5 倍，其余三段 ±3%。表中给中位数，不代表最坏情况。
- **全部为内部基线**：未标定硬件与构建形态前不对外；远程后端未经真实压测，不给 SLA 承诺。
- **未覆盖**：渲染段、多环境并行、真实远程 provider 延迟。整机目前只含四段，不是完整引擎全负载。
