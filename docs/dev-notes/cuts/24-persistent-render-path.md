# 第 24 刀：持久渲染路径（RFC 0004 步 1a）

> **工作记录（2026-11）。** 文中"本机/开发机"指当时跑基准的那台没有 GPU 的机器（llvmpipe 软件光栅化），毫秒数不是 GPU 帧时间，只作同机回归。文中的"补丁"是当时的交付方式，对应关系见[索引](../README.md)。

补丁：`024-persistent-render-path-step1a.patch`（基于 `0387718`，依赖 023）
状态：已落地，**性能目标未达成**（见第三节）

## 一句话

把渲染从"每帧为每个物件新建 GPU 缓冲"改成"上传一次、跨帧复用、同网格同材质的实例一次画完"。2048 个实例的整帧在开发机上从 103 ms 降到 26.6 ms，但每实例边际成本只降了 3–6 倍，没到 RFC 写的"一个数量级以上"。

## 一、做了什么

| RFC 提案 | 落地形态 |
|---|---|
| 资源由调用方持有 | `GpuMesh`（`upload_mesh`）、`GpuMaterial`（`create_material`）上传一次跨帧复用，引擎不做隐式缓存 |
| 实例带模型矩阵 | `Instance` 64 字节行主序，按列上传；`DrawList` 由调用方构造，L5 不持有 World |
| 实例化绘制 | 按（网格 id, 材质 id）稳定排序归段，每段一次实例化绘制；材质因子从顶点挪进 uniform |
| 目标持久、提交即返回 | `RenderTarget` 持久；`render_draw_list` 只提交不轮询；回读走显式 `read_target` |
| 帧循环留在壳层 | `RenderSystem` 默认行为一字未动 |
| 自报统计 | `FrameStats{draw_calls, instances, created_buffers, created_bind_groups, created_textures}`，`created_*` 是相对上一帧的增量 |

新代码在 `crates/oriera-render/src/gpu/persist.rs`，全部在 `render-wgpu` feature 内。`gpu.rs` 只动了三处：`pbr_fragment!` 宏（把 PBR 片元着色器抽出来给两条路径共用）、`pub mod persist;` 与再导出、`HeadlessRenderer` 上一个 `persist` 字段。

现有五个渲染入口没有改任何一行实现逻辑。

## 三、读数（开发机 llvmpipe，**不是 GPU 帧时间**，仅同机回归）

中位数，µs。两条路径的覆盖率逐档一致（86.5 / 83.1 / 90.5 / 93.5%），几何是对齐的。

| 轴 | 966×544，n = 1 / 64 / 512 / 2048 | 1920×1080，n = 1 / 64 / 512 / 2048 |
|---|---|---|
| draw（快照路径） | 10108 / 12339 / 33117 / 103006 | 59955 / 63194 / 80926 / 140783 |
| persist（提交 + 回读） | 9127 / 9981 / 15661 / 26593 | 32261 / 39069 / 43798 / 60879 |
| psubmit（只提交） | 8636 / 9473 / 15617 / 27016 | 30640 / 31778 / 42004 / 58851 |

每实例边际成本：

| 分辨率 | draw | persist | 倍数 |
|---|---|---|---|
| 966×544 | 35–46 | 7–14 | 约 3–6× |
| 1920×1080 | 39–51 | 11（n=64 档 108，见下） | 约 4× |

**差多少**：目标是 10× 以上，实测 3–6×。

1080p 的 persist n=64 档是 108 µs，与相邻档不连贯。psubmit 同档只有 18 µs，说明多出来的时间在回读等待而不是提交，低档位的噪声，不当作结构性结论。

### 残余成本在哪

把网格从 24 顶点方块换成 4 顶点单片，提交代码一字不变，2048 实例的读数：

| 网格 | 整帧 | 每实例边际 | 折合每顶点 |
|---|---:|---:|---:|
| 24 顶点方块 | 30.4 ms | ≈ 9.9 µs | ≈ 0.41 µs |
| 4 顶点单片 | 13.1 ms | ≈ 2.3 µs | ≈ 0.59 µs |

成本跟着顶点数走，折合每顶点 0.4–0.6 µs。所以剩下的每实例成本是软件光栅化在做顶点变换，不在提交路径里。真 GPU 上顶点变换是并行硬件活，量级会不同，但**具体多少现在没人知道**，因为没有真卡读数。

另一个只在软件光栅化上成立的观察：GL 后端下提交本身已部分同步（n=2048 时提交 11.2 ms、整帧 30.4 ms），所以 `psubmit` 在本机不能代表"纯 CPU 提交成本"，RFC 的风险 1（同步等待占比）在真卡上仍未测。

## 四、和 RFC 写的不一样的地方

都是实现时才发现的，已写进文档注释和 RFC 落地清单：

- **空绘制列表是合法帧**，只清屏。快照路径拒收空场景；持久路径面向帧循环，没东西可画也是一帧。
- **相机尺寸必须等于目标尺寸**，否则报错，不画一张被拉伸的图。
- **实例缓冲默认 1024，超出报错**，提示 `reserve_instances`，不自动重建。帧外扩容会如实出现在下一帧的 `created_buffers` 里，且只出现一次。
- **只保证不透明物件正确**。管线没有混合，排序会打乱调用方的绘制顺序。
- **模型矩阵只支持刚体 + 均匀缩放**。法线按旋转部分变换。

## 五、踩坑

**导出错了两次，都是在"把 024 从 023 上剥出来"这一步。**

1. 工作树里 apply 023 后直接 `git add -A` 再 `diff --cached`，结果把 023 的 `Cargo.toml` 和基准文件整个算进了 024。改成：apply 023 → `git add -A` → `git write-tree` 记下树对象 → 拷入 024 的文件 → `git diff --cached <那个树>`。
2. 重做时 `git clean -fdq` 清掉了 `src/gpu/` 目录，`cp` 失败但循环没停，导出的补丁**缺了 `persist.rs`**。`git apply --check` 反而通过了——因为缺文件不影响应用，只是应用出来的东西不完整。这次是靠逐文件 `cmp` 才抓到的。教训：导出后的校验必须包含"补丁里有几个 `diff --git` 头"和"逐文件与工作区比对"，光看 `apply --check` 不够。

**基准对齐，找了很久。** 第一次对齐后 persist n=64 的覆盖率报 13.9%，n=1 报 0%。原因是两个错叠在一起：

- 快照路径只缩放方块的 x、y，z 保持 ±1；模型矩阵里把 z 也缩放了。正面因此离镜头更近、投影变大，角落的方块盖住了左上角。
- 覆盖率函数把"左上角第一个像素"当背景色。左上角一旦被盖住，整片正面都被当成背景，13.9% 其实是方块之间的缝隙。

修法：z 不缩放，与快照路径一致；背景色改成固定值加容差 1。修完覆盖率逐档一致。

**磁盘满。** 第一次在干净工作树跑完整基准时中断，根分区 9.8G 被 `/tmp` 下两个独立编译目录占满，连带工作区的两项测试退出码 101。删掉 023 时代的旧编译目录后重跑，全部通过。两个 101 都是 `No space left on device`，不是代码问题。

**`concat!` 只接受字面量。** 想把 PBR 片元着色器抽成 `const` 共用，`concat!` 报 "expected a literal"。改用 `macro_rules!` 展开成字面量。连带两个约束：`macro_rules` 按文本位置作用域，`pub mod persist;` 必须写在宏定义之后；宏体后面不能带分号。

**两个 `MutexGuard` 字段分别可变借用**（`&mut scratch.order` / `&mut scratch.bytes`）报 E0499。用 `let Scratch { order, bytes } = &mut *scratch;` 解构。
