# 第 25 刀：异步回读（RFC 0004 步 1b）

> **工作记录（2026-11）。** 文中"本机/开发机"指当时跑基准的那台没有 GPU 的机器（llvmpipe 软件光栅化），毫秒数不是 GPU 帧时间，只作同机回归。文中的"补丁"是当时的交付方式，对应关系见[索引](../README.md)。

补丁：`025-async-readback-step1b.patch`（基于 `0387718`，依赖 023、024）
状态：已落地，**本机没有测出收益**

## 一句话

把"回读像素"从一步到位改成"先拿回执、好了再取"，让 CPU 提交下一帧时 GPU 可以接着画。功能与正确性都验过了，但在这台机器上吞吐和同步回读没有差别——软件光栅化下这个收益本来就测不出来。

## 一、先说流程

RFC 给 1b 定的触发条件是"看 1a 的数据决定是否需要"，风险 1 写的是"先在真卡上重跑基准再决定 1b 做不做"。真卡数据没有，**这个条件没有满足**。落地是经项目所有者确认继续的。所以下面只有本机读数，收益大小仍然未知。

## 二、做了什么

| 接口 | 行为 |
|---|---|
| `read_target_async(&RenderTarget) -> ReadTicket` | 把拷贝命令排进队列并开始映射，立即返回，不等 GPU |
| `poll_read(ReadTicket)` | 不阻塞地问一次。没好返回 `Ok(None)`；回执作废或已取走则报错 |
| `wait_read(ReadTicket)` | 等到就绪并取走像素 |
| `reads_in_flight()` | 还在 GPU 侧没完成的张数 |
| `MAX_READS_IN_FLIGHT = 4` | 在途上限，也是已完成待取的上限 |

两条约束都是为了不无限占内存：

- **在途满 4 张时，`read_target_async` 阻塞到最旧的完成。** 这是背压，不是悄悄排队。
- **已完成但没人取的像素最多留 4 张，再多丢最旧的。** 一张回执如果在之后又发起了 4 次请求之前没被取走，它就作废了，取的时候报错。不会把缓冲里后来的内容当成它。

回读缓冲按需进池复用。池子长出来的那几次创建会出现在之后那帧的 `FrameStats::created_buffers` 里；同步 `read_target` 是一次性的，照旧不计。

公开面只增不改，全部在 `render-wgpu` feature 内，默认 feature 不编译。`gpu.rs` 只动了再导出。

## 四、读数：本机没有收益

llvmpipe，中位数，ms/帧。`pasync` 是两帧在途、8 帧均摊的吞吐口径。

| 分辨率 | n = 1 / 64 / 512 / 2048 | 同步回读 `persist` | 流水 `pasync` |
|---|---|---|---|
| 966×544 | | 9.0 / 10.0 / 15.5 / 20.5 | 8.1 / 8.9 / 14.3 / 23.9 |
| 1920×1080 | | 30.5 / 31.7 / 43.0 / 59.6 | 33.8 / 32.9 / 42.7 / 59.3 |

两轴互有高低，差异都在噪声里。

**为什么测不出来**，两条原因都只在软件光栅化上成立：

- 所谓 GPU 就是 CPU。让提交和光栅化并行，等于让它们抢同一批核心。
- `psubmit` 与 `persist` 读数接近，说明提交本身已经占了大部分时间，留给流水去重叠的空间很小。

**顺带发现一个之前没注意的问题**：同一档位跨轮次的波动很大。`persist/2048` 在 544p 下，第 24 刀那次是 26.6 ms，这次是 20.5 ms，相差两成多，同机同配置。所以个位数百分点的差别不能当结论，第 24 刀里 2048 实例的读数应该理解成"20–27 ms"这个区间。这不改变第 24 刀的结论（3–6 倍 vs 目标 10 倍），但说明本机基准只适合看量级，不适合看细节。

支持 1b 的目前只有结构上的理由：同步回读让 CPU 等 GPU 画完、GPU 再等 CPU 提交下一帧，两头都有空档。没有测量证据。真卡基线仍是待办，而且现在它同时决定两件事：1a 的目标差多少，1b 到底值不值。

## 五、踩坑

**三个测试错，实现没问题。**

1. B3 数出 4 块缓冲而不是 1 块。统计的是"相对上一帧新建了多少"，而开始计数前上传了网格（2 块）和材质（1 块），这 3 块都算进了第一帧。先渲一帧冲掉就好。和第 24 刀"容量测试误以为扩容不计入"是同一类错：这套计数是增量口径，数之前要先对零。
2. B3 的预期值也写错了：池子从 1 块长到 4 块只新建 3 块，预期值写成了 4 块。
3. B4 的断言写反了。"先作废一批、后面都保留"是正确行为，却在"保留"分支里断言"之前不能出现过作废"。打印出实际顺序才发现：前 8 张作废、后 4 张保留，实现对，断言错。

**一次是字符串里的半角引号把 Rust 字符串截断了。** 写基准表注时用了 `"…"`，编译报 `expected ','`。表注这类文字现在一律用中文引号。

**一次是脚本替换到一半断言失败，后面的修改没落盘，但当时的编译和测试照跑了。** 结果是看到的报错里混着"已经修过"的旧问题。脚本里多个替换要么全成功要么全不写，跑之前先确认脚本退出码。

## 六、已知瑕疵

作废回执的错误走的是 `GpuError::Device`，显示出来是 `device init failed: read ticket … is unknown, already taken or was dropped`。前半句词不达意。`GpuError` 只有三个变体，没有合适的；加变体是公开类型变更，不在这一步动。已经登记在 RFC 落地清单里。

## 七、没做的

- 蒙皮网格的持久路径。演示里的人形都是蒙皮网格，现在仍走每帧新建缓冲的旧路径，1a 和 1b 对它们都不起作用。
- 窗口与交换链（步 2，需完整评审）。
- 把真实帧时间喂给 `RenderSystem` 的自适应调速。
- 真 GPU 基线。

## 八、建议的下一步

渲染这条线上，**在没有真卡之前继续做下去的边际价值已经很低**。1a 的目标差多少、1b 值不值、每实例 7–14 µs 里有多少是真卡上也会有的，三个问题都卡在同一件事上。

所以当时先停在这里，下一步二选一：

1. **找一台有 `/dev/dri` 的机器**，把 `gpu_frame` 五轴跑一遍。半小时的事，能一次回答上面三个问题，再决定渲染线怎么走。
2. 如果机器一时拿不到，**转去蒙皮网格的持久路径**。它的价值不依赖性能读数——演示里的人形需要它才能走持久路径，正确性在本机就能验。但它比 1a/1b 都大：关节矩阵要进 uniform 或纹理，有上限，RFC 里原来明确划在范围外，需要单独确认。
