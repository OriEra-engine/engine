# 性能测试矩阵与指标口径

> **工作记录（2026-11）。** 文中"本机/开发机"指当时跑基准的那台没有 GPU 的机器（llvmpipe 软件光栅化），毫秒数不是 GPU 帧时间，只作同机回归。文中的"补丁"是当时的交付方式，对应关系见[索引](../README.md)。

- 日期：2026-11-24
- 范围：全仓库按引擎层（L2 调度 → L3 ECS → L6 物理 → L7 推理编排/路由 → L9 记忆 → L4 资产）
- 定位：性能测试的**场景清单与指标口径**；哪些离线可测、哪些受前置约束，一并列明
- 关联：RFC 0003（SLA 分级）、#13 包装层接线方案、补丁 007/008/009

## 一、为什么要先定口径

仓库纪律里有两条直接影响性能测试的硬约束：

1. **金样字节稳定 / 确定性**——rule 档同种子逐位可复现，性能数字才能跨版本回归对比。没有确定性基线的压测数字只能看个热闹。
2. **正确性与性能分账**——MuJoCo 对拍的 `|dq|`、召回质量这类质量门不混进耗时指标；`0.0005 rad` 是实测偏差值，容差 `0.05 rad`，不能当耗时阈值反过来用。

所以本矩阵每个场景都标了：**量什么 / 怎么量 / 离线能不能测**。

### 真实后端侧（接云链后压，当前受前置约束）

以下指标只在 rule 双跑 harness 钉死、跨层审批通过后才进入压测范围：

- 首 token 时延、completion p50/p95；
- 重试次数、降级跳数、熔断开合次数；
- 缓存命中 token 占比；
- 每千次调用成本（`CostMeter`，µ-currency，按 `ModelPrice` 牌价估算）。

## 三、横切口径

- **百分位优先**：p50 看典型、p95/p99 看尾延迟，均值只作参考；抖动（标准差、max−min）单列。
- **确定性基线**：同一机器、同一 release 构建、同一 seed；数字跨版本对比才有意义。
- **质量与性能分账**：对拍偏差、召回相关性、金样指纹属于质量门，不与耗时混记。
- **成本/token 单列**：cached 命中率、每千回合 µ-currency，与延迟分开看。
- **内存长跑**：N tick soak 后常驻内存、有无泄漏；与短跑分列。
- **独立 target**：干净复现一律独立 `CARGO_TARGET_DIR`，共享 target 残留旧二进制会污染金样/fixture。

### router `resolve`（纯函数决策，不持实例不记台账）

| 场景 | 耗时（中位） |
|---|---|
| chain_len 2，首项即中 | ~29 ns |
| chain_len 4，首项即中 | ~29 ns |
| chain_len 8，首项即中 | ~29 ns |
| degraded_k 1（1 项不可用） | ~45 ns |
| degraded_k 3 | ~61 ns |
| degraded_k 7 | ~139 ns |
| all_unavailable（fail closed） | ~121 ns |

读法：决策成本随下探深度线性增长（每多跳一候选 ≈ 15–20 ns），首项即中时与链长无关——`resolve` 对候选列表是按 id 查找，不是全表扫描。**ns 级开销不构成帧预算压力**，步 C 包装层接入不会因决策本身引入可感知延迟。

### memory `retrieve`（离线关键词打分）

| 场景 | 耗时（中位） |
|---|---|
| local n=60, k=5 / k=10 | ~78 µs / ~80 µs |
| local n=120, k=5 / k=10 | ~160 µs / ~159 µs |
| local n=240, k=5 / k=10 | ~324 µs / ~316 µs |
| layered s60/l120, k=10 | ~246 µs |
| layered s120/l240, k=10 | ~470 µs |
| record n=60 / n=240 | ~1.1 µs / ~4.4 µs |

读法：检索线性于参与打分的条目数（约 1.3 µs/条），top-k 几乎不影响成本（打分是全量扫描，k 只决定截取）。分层后端两层合并打分约等于两层条目数之和的成本，无额外常数。**单次检索在百微秒量级**——若放进帧内同步调用（60fps 预算 16.6 ms），一次 240 条检索约占 2%，需要注意调用频次，建议走帧外或限频。

#### 倒排索引后端对照（022，中文夹具，k=10，60 样本，release）

`cargo bench -p oriera-agent --bench memory -- --nocapture indexbench`

| n | 全量扫描 p50/p99 µs | 倒排索引 p50/p99 µs | p50 倍数 |
|---|---|---|---|
| 1000 | 1295.4 / 1488.4 | 607.5 / 3001.1 | 2.13× |
| 5000 | 6376.9 / 6937.5 | 3040.0 / 3242.5 | 2.10× |
| 20000 | 28691.0 / 29862.9 | 13962.3 / 15094.1 | 2.05× |

**5× 目标未达标，如实记录**：实测 p50 改善 2.05–2.13×。原因分析：

1. 无损剪枝边界保守——零命中条目仍可靠 importance / recency / about_bonus 过闸，kth 候选分数低于非候选上界（5×iw + rw + ab = 5.45）时显式回退全量扫描，部分请求没走索引路径；
2. 候选条目仍要现场构造条目 bigram 集合并做 `contains` 扫描，单候选成本与全扫描单条同构，省的只是被剪掉条目的 gram 构造；
3. 查询 7 gram 的并集跨条目复用，候选集大于严格命中集（1/3）；
4. posting 遍历与 HashSet 去重有常数开销，小窗口被抵消。

1000 档索引 p99（3001 µs）反超扫描（1488 µs），回退路径叠加索引冷启动是直接原因。该后端为 opt-in 内部原型，未接默认装配，不进 release note 与对外材料。

### infer `InferJobs` 编排（后端立即返回，纯编排开销）

| 场景 | 耗时（中位） |
|---|---|
| poll_empty（空轮询） | ~11 ns |
| submit_drain（单 job 全周期） | ~55 µs |
| burst n=1 cap=1 | ~54 µs |
| burst n=4 cap=4 | ~181 µs |
| burst n=8 cap=8 | ~361 µs |
| burst n=8 cap=4 | ~301 µs |
| burst n=16 cap=8 | ~580 µs |

读法（三条对 #13 步 C 直接有用）：

1. **空轮询是纳秒级固定税**（11 ns），帧循环每帧调一次无负担。
2. **单 job 全周期 ~55 µs，几乎全是 OS 线程 spawn + channel 往返**——`InferJobs` 是"一 job 一线程"模型。这不是模型耗时，是编排自身的地板价。
3. **成本随实际提交数线性增长（~45 µs/job），cap 只截断不摊薄**：n=8 cap=4 比 n=8 cap=8 省的是被拒的那 4 个提交，已接受的 job 单价不变。所以**提高 `max_inflight` 不会让单 job 更便宜，只会允许更多并发**。

对包装层的约束：Realtime 档 per-frame deadline 必须覆盖提交开销；若 deadline 设得比 ~55 µs 还紧，"超时即降级"会先被自己的编排成本触发，降级风暴而非真的后端慢。建议 Realtime 槽位 deadline 下限按 **≥ 1 ms** 起步（留 20 倍余量给线程调度抖动），实际值待接真实后端压测后回调。

#### 尾延迟分位数（021，离线 RuleProvider，复用池，3 轮 × 60 样本，release）

`cargo bench -p oriera-infer --bench jobs -- --nocapture tails`

| 并发 | p50 µs | p95 µs | p99 µs | 轮间 p50 极差 µs | 每 job p50 µs |
|---|---|---|---|---|---|
| 1 | 31.9 | 59.2 | 89.3 | 8.4 | 31.9 |
| 4 | 100.5 | 500.4 | 1106.6 | 8.4 | 25.1 |
| 16 | 349.9 | 896.1 | 1284.7 | 22.7 | 21.9 |

读法：p50 每 job 22–32 µs，随并发摊薄；尾延迟在并发 4/16 明显抬升，p99 到 1.1–1.3 ms，是 OS 线程 spawn 竞争的尾方差，不是吞吐问题。轮间 p50 极差 1/4 并发 8.4 µs，16 并发 22.7 µs——高并发档轮次波动同步放大。该证据供线程池 RFC 立项与 Realtime deadline 余量拍板；离线 RuleProvider 不含模型/网络时间，远程后端压测另计。

### GLB 解码与 L8 闸口

| 场景 | 耗时（中位） |
|---|---|
| decode 1k 顶点 | ~8.7 µs |
| decode 10k 顶点 | ~55 µs |
| decode 50k 顶点 | ~258 µs |
| decode 100k 顶点 | ~524 µs |
| gate valid 1k / 10k / 50k | ~9.3 µs / ~55 µs / ~256 µs |
| gate reject 60k / 100k | ~310 µs / ~528 µs |

读法（三条对 L8 阈值回调直接有用）：

1. **解码线性于顶点数，约 5.2 ns/顶点**（含法线与索引），1k 顶点有 ~8 µs 的 JSON chunk 解析固定成本。100k 顶点半毫秒级。
2. **闸口本身几乎零开销**：`gate valid` 与 `decode` 逐档持平（差值在噪声内）——三道核对（顶点/三角/半长）是 O(1) 比较，成本全在解码。
3. **拒绝不比通过便宜，甚至更贵**：超限资产必须**完整解码后**才在顶点核对处被拒，60k 顶点的拒绝（~310 µs）比 50k 的通过（~256 µs）还慢。这是 fail closed 的代价——闸口不读解码器没读的字节，所以无法在解码前预判。

对 L8 阈值的意义：默认闸 50k 顶点 / 100k 三角 / 2.0 m 是宽松起步值。按这条曲线，**即使放到 100k 顶点，单资产闸口成本也只有 ~0.5 ms**，对帧预算无压力（且资产校验本就该在帧外）。所以阈值收紧的理由应该是**下游渲染/物理承载能力**，而不是闸口自身的耗时。若未来要防"超限大文件耗尽解码预算"，需要的是**字节上限前置**（`max_bytes` 已在解码前生效），而不是调顶点闸。

### core 帧循环（`Scheduler::tick`，空系统）

| 场景 | 耗时（中位） |
|---|---|
| empty（零系统） | ~80 ns |
| systems_n 1 / 4 / 16 / 64 | ~142 ns / ~323 ns / ~940 ns / ~3.58 µs |
| systems_n16_squeezed（allocator 压到地板） | ~940 ns |

读法：调度器地板价 ~80 ns，**每个系统 ~54 ns 摊销**（动态分发 + `Instant` 计时 + grant 读取）。64 个系统也只有 3.6 µs——按 16.6 ms 帧预算算，调度税可忽略，帧时间几乎全在业务系统里。**调速态与未调速同价**：allocator 的 squeeze 只改 grant 表的值，不增加分发路径长度，所以调速本身不引入额外开销。

### 物理步（`PhysicsSystem` 粒子积分 / `MultibodySystem` 关节链）

| 场景 | 耗时（中位） |
|---|---|
| particles 运动 1k / 5k / 20k 实体 | ~1.67 µs / ~8.4 µs / ~33.4 µs |
| particles 静止 1k / 5k / 20k 实体 | ~1.69 µs / ~8.4 µs / ~33.9 µs |
| multibody_step 1 / 4 / 16 props | ~30 µs / ~44 µs / ~53 µs |

读法（两条）：

1. **粒子积分线性，约 1.65 ns/实体**，20k 实体一帧 33 µs，占 60fps 预算 0.2%。ECS 列扫描 + 积分非常便宜。
2. **`idle_frames` 快路径不省时间，只保语义**：静止世界与运动世界逐档持平（1.69 vs 1.67 µs）。这是**设计如此，不是回归**——`PhysicsSystem` 的 idle 判定要全量扫一遍列确认"全部在内且全静止"才能跳过写入，扫描成本等于积分成本。它的价值是保证跳帧时世界状态逐位不变（`frozen_time_skips_the_pass_bit_identically` 测试钉的就是这个），不是省算力。若未来需要真正的省算力 idle 路径，得靠脏标记或休眠岛，而不是当前的扫描判定。
3. **`MultibodySystem` 单步 ~30 µs 起，prop 增长近乎平坦**（1→16 props 只多 23 µs）：4-DoF 关节链求解是大头，自由刚体 prop 便宜。按 60 Hz 步进，一帧物理约 0.05 ms，具身训练可跑到数千倍实时。

## 五、缺口与下一步

- **微基准已覆盖全部纯计算热点**：core 帧循环、ECS 查询、物理步（粒子/关节链）、splat、路由决策、作业编排、记忆检索、GLB 闸口——六处新增 + 两处原有，覆盖 L2/L3/L4/L6/L7/L9，全部离线可测、确定性可复现。
- 仍未建：
  - **长跑 soak 脚本**（内存 + 热身后稳态）：微基准量的是单次成本，不覆盖 N 万帧后的内存增长与调度漂移；
  - **真实后端压测 harness**：首 token 时延、completion p95、缓存命中率等指标受 rule 双跑前置约束，未进入压测范围；
  - **GPU 渲染实测**：splat criterion 量的是 CPU 侧数据准备，真机帧率需带 GPU 环境。
- 基准用途定位：**同机回归对比**。跨机器数字不可直接比（尤其 `infer_jobs` 含 OS 线程 spawn、`frame` 含 `Instant` 精度差异）。

## 六、口径红线（沿用前序）

- 不写"端侧实时"（端侧 ONNX Runtime 在 2027 H2）；
- 性能数字只作内部基线，未标定硬件与构建形态前不对外；
- 远程后端未经真实压测，不对外给 SLA 承诺。
