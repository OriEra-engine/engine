# 三候选场景规模定标 · 哪个对引擎最友好

> **工作记录（2026-11）。** 文中"本机/开发机"指当时跑基准的那台没有 GPU 的机器（llvmpipe 软件光栅化），毫秒数不是 GPU 帧时间，只作同机回归。文中的"补丁"是当时的交付方式，对应关系见[索引](../README.md)。

补丁 **019**（多环境并行缩放基准）。基于实测曲线反推，不是拍脑袋估。

## 一、结论先说

**具身智能训练最友好，互动内容次之，危险化工最不友好。**

但理由不是"哪个更快"，而是**三个场景压的是完全不同的轴，只有一个轴是引擎现在的短板**：

| 场景 | 绑定约束 | 引擎现状 |
|---|---|---|
| 具身训练 | 环境步/秒（吞吐） | **避开全部已知短板** |
| 互动内容 | 记忆规模 + 实时 deadline | 撞短板，但**可解** |
| 危险化工 | 领域能力（气体/传感/因果） | **缺的是能力，不是性能** |

## 二、新增实测：多环境并行缩放

此前所有数据都是"一个世界"。具身训练要 N 个世界同步进，这是另一根轴，必须实测。

每环境 4 props + 60 条记忆 + 一次推理闭环（离线 RuleProvider）：

| envs | phys | phys+mem | +infer | infer 边际 |
|---|---|---|---|---|
| 1 | 52.8 | 74.0 | 107.4 | 33.4 |
| 8 | 431.1 | 623.3 | 896.8 | 273.5 |
| 32 | 1732.1 | 2455.1 | 3642.6 | 1187.5 |
| 64 | 3489.7 | 4927.7 | 7335.0 | 2407.2 |
| 128 | 7226.0 | 10128.5 | 15251.1 | 5122.6 |

（µs/步）

**每环境摊销几乎持平**：108.8 → 120.3 µs（1→128 环境只涨 11%）。**没有悬崖，近线性。**

吞吐视角：

| envs | 步/秒 | 环境步/秒 |
|---|---|---|
| 1 | 9127 | 9127 |
| 32 | 278 | 8905 |
| 128 | 63.7 | **8155** |

**环境步/秒稳定在 8000–9000，与环境数无关。** 这是引擎当前的训练吞吐天花板（离线后端）。

### 一个容易搞错的对照

第一版把"逐个提交收割"和"全提交后收割"对比，得出并发快 6 倍。**那是错的**——并发档只做了 submit+drain，串行档却含物理和记忆，口径不一致。

修正成同口径后：

| envs | 逐个提交收割 | 全提交后收割 | 批量/逐个 |
|---|---|---|---|
| 8 | 888.5 | 787.2 | 0.89x |
| 32 | 3602.1 | 3173.2 | 0.88x |
| 128 | 15499.2 | 13242.5 | **0.85x** |

**批量提交只省 12–15%**，不是 6 倍。因为物理+记忆在主线程串行，占了大头（75 µs/env vs infer 33 µs/env）。

**推论**：`InferJobs` 线程模型即使改成线程池，训练吞吐上限也只能提升约 15%——**它不是训练的瓶颈**。这进一步下调了线程池改造的优先级。

## 三、三场景规模估算

以下规模是**工程估算**，标注为假设；单位成本来自实测。

### 场景 A · 具身智能训练

| 维度 | 估值 | 依据 |
|---|---|---|
| 并行环境 | 32–128/进程 | 实测到 128 仍线性 |
| 每环境记忆 | 0–100 条 | episode 短，多为任务状态而非长期记忆 |
| 物理规模 | 1 臂 + 4–16 props | 与实测夹具同档 |
| 推理频率 | 每步或每 k 步 | LLM 在环时由模型延迟主导 |
| 帧率约束 | **无 60fps 硬约束** | 吞吐导向，可 headless |

**成本**：约 110 µs/环境/步 → **8000–9000 环境步/秒**。

换算训练时长：
- 1e7 步 ≈ **20 分钟**
- 1e8 步 ≈ **3.4 小时**

**为什么最友好**：
1. 记忆窗口小 → **完全避开 0.58 µs/条的线性悬崖**；
2. 无实时 deadline → **线程模型的高方差伤不到它**（方差只影响尾延迟，不影响总吞吐）；
3. 近线性缩放，加进程就能加吞吐；
4. 若 LLM 真在环，模型延迟 100 ms–1 s，引擎那 110 µs 完全淹没在里面——**引擎根本不是瓶颈**。

**唯一风险**：8000 环境步/秒对大规模 RL 偏慢。但那要靠多进程/多机横向扩，不是靠改引擎内部结构。

### 场景 B · 危险化工 / 应急处置 / 安全培训

| 维度 | 估值 | 依据 |
|---|---|---|
| 并行环境 | 1–8 | 人在环演练 |
| 记忆规模 | 2000–20000 条 | 规程、预案、设备台账、事故案例 |
| 物理需求 | **气体扩散、流体、传感器噪声、事故因果链** | 场景本质 |
| 帧率 | 60fps；VR 培训可能 90fps | 人在环 |

**成本**：记忆 20000 条 → **11.7 ms/检索 = 70% 帧预算**，其它什么都别干了。

**但这不是最致命的。** 最致命的是：**引擎现在没有气体扩散、没有传感器噪声模型、没有事故因果链**。有 rigid3d、GLB、splat，这些是刚体与外观，不是过程模拟。

**为什么最不友好**：性能问题花钱能解，能力缺口不是。加多少基准、改多少索引都填不上这个洞。

**一个转机**：规程知识若走 RAG 后端而不是 `MemoryStore` 全量扫描，记忆悬崖就不存在——这正好是 002/008 那两刀后端抽象的价值所在。**所以记忆问题可绕过，领域能力不能。**

### 场景 C · 互动内容 / 智能体（长期陪伴、开放世界）

| 维度 | 估值 | 依据 |
|---|---|---|
| 世界数 | 1 | 单世界 |
| NPC 数 | 10–100 | 城市开放世界 demo 形态 |
| 每 NPC 记忆 | 5000–50000 条 | 长期陪伴累积 |
| 帧率 | **60fps 硬约束** | 交互体验 |
| 推理 | 真实 LLM，100 ms–2 s，异步 | 远程后端 |

**成本**：单 NPC 5000 条 = 2.95 ms。若 100 NPC 每帧全检索 = **295 ms/帧**，彻底不可行。

当然实际不会每帧全检索——按需触发（对话时）就行。但这要求**检索必须移出帧循环或严格限频**，是架构约束不是优化选项。

**为什么次友好**：撞两个短板（记忆规模、deadline 方差），但**两个都有明确解法**：
- 记忆：换后端（RAG/倒排）、分层窗口、限频；
- deadline：异步化 + 按尾延迟留余量。

不像化工那样缺的是整块能力。

## 四、一个可以直接用的设计约束

60fps 下，若给记忆检索分配 **10% 帧预算**（1667 µs）：

\[
\text{窗口上限} = \frac{1667}{0.58} \approx 2870 \text{ 条}
\]

放到 30% 预算则约 **8620 条**。

**这就是当前全量扫描架构的硬边界**：60fps 场景下，单 agent 记忆窗口超过约 3000 条就必须换后端或限频，没有第三条路。

- 场景 A：远低于此，安全；
- 场景 B：2000–20000 条，**跨越边界**，必须换 RAG 后端；
- 场景 C：5000–50000 条，**远超边界**，必须换后端。

## 六、诚实边界

- 三场景的**规模数字是工程估算**，不是实测；单位成本（0.58 µs/条、110 µs/环境/步、8155 环境步/秒）是实测。
- 训练吞吐用**离线 RuleProvider**，不含真实模型延迟。LLM 在环时吞吐由模型决定，本文数字是引擎侧上限。
- 多环境基准是**单进程串行步进**，未测多进程/多机横向扩展，也未测 GPU 物理。
- 化工场景的能力缺口判断基于当前 crate 面（rigid3d / glb / splat），未做外部方案调研。
- 全部性能数字为内部基线，未标定硬件与构建形态前不对外。
