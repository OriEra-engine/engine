# RFC 0004 — 渲染持久路径：从"渲染一张快照"改为"持续出帧"

- 状态 / Status: **草案 / Draft**；**步 1a 已落地**（2026-11-25，经项目所有者确认走 GOVERNANCE 的"不跨层新增 feature"快车道）；**步 1b 已落地**（同日）；**步 1c 已落地**（同日，超出本 RFC 原定范围，见落地清单与第 6 节）；步 2（窗口与交换链）仍走完整 RFC 流程；**真卡复核已补**（同日，见三份落地清单之后）
- 影响契约 / Contract: 无 schema 变更。新增 `oriera_render::gpu` 下的类型与入口，全部在 `render-wgpu` feature 内；现有五个渲染入口**不动**
- 性质 / Nature: 能力补全（新增持久资源 + 实例化绘制 + 显式回读），非破坏，默认关
- 影响层 / Layers: 仅 L5（`crates/oriera-render`）
- 关联 / See also: `docs/ARCHITECTURE.md` L5 节、`docs/STABILITY.md` 已知不稳定边界、`docs/PERF.md`、`GOVERNANCE.md`

## 步 1a 落地清单（2026-11-25）

实现（`crates/oriera-render/src/gpu/persist.rs`，全部在 `render-wgpu` feature 内，现有五个渲染入口未动）：

| RFC 提案 | 落地形态 |
|---|---|
| `GpuMesh` | 顶点 32 字节（位置 3 + 法线 3 + UV 2），材质因子移出顶点；`upload_mesh` 在 CPU 侧拒绝空顶点、空索引、法线/UV 长度不符、索引越界 |
| `GpuMaterial` | 因子进 32 字节 uniform，纹理与采样器进绑定组；`create_material` |
| `Instance` / `DrawList` | 行主序模型矩阵，按列上传；`DrawList` 由调用方构造，L5 不持有世界 |
| `render_draw_list` | 实例按（网格 id,材质 id）稳定排序归段，每段一次实例化绘制；排序下标与矩阵字节走复用暂存区，帧内不堆分配；**提交后即返回** |
| `RenderTarget` / `resize_target` / `read_target` | 目标持久；改尺寸显式；回读是独立方法，也是该路径唯一的同步点 |
| `FrameStats` | 自报 `draw_calls` / `instances` 与相对上一帧的新建缓冲、绑定组、纹理数；创建计数集中在一处，文件内每个 `create_*` 后紧跟一句计数 |
| 片元着色器 | 抽成 `pbr_fragment!` 宏，快照路径与持久路径共用同一份源码（`concat!` 只接受字面量，故用宏而非常量） |

与提案的三处出入（均为实现期发现，已写进对应文档注释）：

- **实例缓冲容量**：默认 1024 个实例，`render_draw_list` 超容量时返回错误并提示 `reserve_instances`，不自动重建——与提案一致；`FrameStats.created_*` 是"相对上一帧"的增量，所以帧外的扩容会如实出现在下一帧里且只出现一次。
- **空绘制列表是合法帧**（只清屏）。快照路径拒收空场景，持久路径面向帧循环，没有东西可画也是一帧。
- **相机尺寸必须等于渲染目标尺寸**，否则报错，而不是画出一张被拉伸的图。

验收（断言 A1–A6）：

| 断言 | 结果 |
|---|---|
| A1 像素等价 | 通过：同一网格、单位矩阵、同一材质，与 `render_scene_views` **逐像素一致**（差异像素 0） |
| A2 稳态零新建 | 通过：预热后 100 帧（实例持续移动）新建缓冲 / 绑定组 / 纹理均为 0 |
| A3 实例化 | 通过：64 实例 1 次绘制；两种材质 2 次；再加一种网格 3 次 |
| A4 提交不同步 | 结构保证 + 行为测试：连续渲染后才回读 |
| A5 现有行为不变 | `oriera-render --features render-wgpu` 原有 18 passed / 3 ignored 不变；默认 feature 不编译新代码；clippy `-D warnings` 零告警 |
| A6 基准对照 | `gpu_frame` 新增 `persist`（提交 + 显式回读，与 `draw` 同口径）与 `psubmit`（只提交）两轴，覆盖率与 `draw` 逐档一致 |

**性能目标在开发机上未达成，如实记录。**（真卡上成立，见下面的"真卡复核"；这一节保留开发机的原始记录。）目标是每实例边际成本比快照路径低一个数量级以上；在开发机（llvmpipe 软件光栅化，非 GPU 帧时间）上实测：

- 每实例边际成本 35–46 µs → 7–14 µs，约 **3–6 倍**，不到一个数量级；
- 2048 实例整帧：544p 103 ms → 26.6 ms，1080p 141 ms → 60.9 ms。

残余成本不在提交代码里：把网格从 24 顶点方块换成 4 顶点单片（提交代码完全相同），2048 实例的每实例边际从约 9.9 µs 降到约 2.3 µs，折合每顶点都是 0.4–0.6 µs——即软件光栅化的顶点变换。另：GL 后端下 `psubmit` 与 `persist` 读数接近，说明提交本身已部分同步，该轴在本机不能代表"纯 CPU 提交成本"。两项结论都只在软件光栅化上成立；真卡上重跑的结论相反——每实例边际消失、同步回读才是大头，见"真卡复核"。

**没做**：蒙皮网格的持久路径、窗口与交换链（步 2）、把真实帧时间喂给 `RenderSystem` 的自适应调速。

## 步 1b 落地清单（2026-11-25）

**先说明流程**：上表给 1b 定的触发条件是"看 1a 的数据决定是否需要"，风险 1 写得更明确——先在真卡上重跑基准再决定。真卡数据没有，这个条件没有满足。落地是因为项目所有者指示继续；收益大小因此仍然未知，下面只报本机读数。

实现（同在 `render-wgpu` feature 内，`gpu/persist.rs` 追加，公开面只增不改）：

| 接口 | 行为 |
|---|---|
| `read_target_async(&RenderTarget) -> ReadTicket` | 把拷贝命令排进队列并开始映射，立即返回，不等 GPU |
| `poll_read(ReadTicket)` | 不阻塞地问一次；没好返回 `Ok(None)`，回执作废或已取走则报错 |
| `wait_read(ReadTicket)` | 等到就绪并取走像素 |
| `reads_in_flight()` | 还在 GPU 侧没完成的张数 |
| `MAX_READS_IN_FLIGHT = 4` | 在途上限，也是已完成待取的上限 |

两条内存约束：

- 在途满 4 张时，`read_target_async` 阻塞到最旧的完成（背压），不悄悄排队。
- 已完成但没人取的像素最多留 4 张，再多丢最旧的。一张回执如果在之后又发起了 4 次请求之前没被取走就作废，取的时候报错——不会把缓冲里后来的内容当成它。

回读缓冲按需进池复用。池子的增长出现在之后那帧的 `FrameStats::created_buffers` 里；同步 `read_target` 是一次性的，照旧不计。

测试（`tests/persist_path.rs` 追加 5 条，共 16 条，全部 `#[ignore]`，本地 16 passed）：

| 断言 | 结果 |
|---|---|
| B1 逐帧一致 | 通过。12 帧各不相同；深度 1（提交后立刻等）与深度 4（四帧都提交再取）两种取法都与"渲染后立刻同步回读"逐字节相同 |
| B2 轮询 | 通过。没好返回 `Ok(None)`；就绪后像素一致；同一回执第二次取报错 |
| B3 缓冲复用 | 通过。一张一张取只新建 1 块缓冲；四帧在途再新建 3 块；之后零新建 |
| B4 背压与作废 | 通过。连续发起 12 次不取，在途始终 ≤ 4；作废的恰是最旧的 8 张，保留的 4 张像素与各自帧一致 |
| B5 改尺寸 | 通过。回执记着提交时的尺寸，目标改尺寸后在途那张读出来仍是旧尺寸旧画面 |

基准加第五轴 `pasync`：两帧在途、8 帧均摊，吞吐口径。

**本机没有测出吞吐收益**（llvmpipe，中位数，ms/帧）：

| 分辨率 | n = 1 / 64 / 512 / 2048 | 同步回读 `persist` | 流水 `pasync` |
|---|---|---|---|
| 966×544 | | 9.0 / 10.0 / 15.5 / 20.5 | 8.1 / 8.9 / 14.3 / 23.9 |
| 1920×1080 | | 30.5 / 31.7 / 43.0 / 59.6 | 33.8 / 32.9 / 42.7 / 59.3 |

两轴互有高低，差异在噪声内。原因有两条，都只在软件光栅化上成立：所谓 GPU 就是 CPU，提交与光栅化并行等于抢同一批核心；`psubmit` 与 `persist` 接近说明提交本身已占大部分时间。另需注意同一档位跨轮次的波动：`persist/2048` 两次运行分别是 26.6 ms 与 20.5 ms，相差两成多，个位数百分点的差别不能当结论。

支持 1b 的目前只有结构上的理由（同步回读让 CPU 与 GPU 轮流空等），没有测量证据。真卡上补测的结果见"真卡复核"：**就单帧时间而言没有收益**，与这里相同。

已知瑕疵：作废回执的错误走 `GpuError::Device`，显示为 "device init failed: read ticket …"，前缀词不达意；改公开错误类型不在本步范围。

## 步 1c 落地清单（2026-11-25）

**先说明流程**：第 6 节原本把蒙皮路径划在本 RFC 范围之外，理由是每实例一份关节面板、涉及 uniform 容量上限，复杂度高于静态网格，等 1a 有数据再议。落地是因为项目所有者指示继续（原话：有没有暂时不需要跑在主机上的任务，先执行那个——蒙皮与纯 CPU 侧的回读、等价测试都不需要真卡）。既然落了，就把它当作 RFC 范围内的增量一并登记，第 6 节同步改写为已落地。

语义沿用快照路径：顶点在 bind 空间，面板是 bind→世界的 4×4（行主序上传、着色器按列读），模型的刚体变换由调用方**预乘进面板**，因此蒙皮实例**没有** model 矩阵。

| 接口 | 行为 |
|---|---|
| `upload_skinned_mesh(positions, normals, uvs, joints, weights, indices)` | 一次上传；校验非空、长度一致、索引在范围内、关节号 < 256；记下网格用到的最大关节号 |
| `GpuSkinnedMesh` | 顶点 64B（pos/normal/uv + JOINTS Uint32×4 + WEIGHTS Float32×4），无 `id` |
| `create_skeleton()` / `update_skeleton(&GpuSkeleton, palette)` | 骨架持 16KB uniform（`SKELETON_CAPACITY = MAX_JOINTS = 256`）；面板 1..=256 个，按列写，同时记 `joint_count()` |
| `SkinnedInstance { mesh, material, skeleton }` / `SkinnedDrawList` | 与静态 `DrawList` 平行的独立列表 |
| `render_frame(&DrawList, &SkinnedDrawList, camera, target)` | 一次清屏一个 pass：先静态归段绘制，再逐个蒙皮实例切管线、绑 camera/material/joints 三组、`draw_indexed` |
| `FrameStats::skinned_draws` | 本帧蒙皮绘制次数 |

排版要点：蒙皮着色器与静态路径共用同一份片元着色器（`pbr_fragment!` 宏），所以顶点输出结构、全局绑定名必须一致（`VSOut` / `cam` / `base_tex` / `mr_tex` / `base_samp`），换名字会在创建 shader module 时就 validation error。管线无混合，深度 `Depth32Float` Less + write。

渲染前逐实例校验 `mesh.max_joint < skeleton.joint_count()`，不满足报 exceeds skeleton palette length …; call update_skeleton——没写面板、写少了都不会静默画错。

测试（`tests/persist_path.rs` 追加 4 条，共 20 条，全部 `#[ignore]`，本地 20 passed）：

| 断言 | 结果 |
|---|---|
| S1 与快照路径逐像素一致 | 通过。同一姿势下 `render_skinned_views` 与持久蒙皮路径差异 0；同帧 `skinned_draws=1`、`draw_calls=1`、`instances=0` |
| S2 换面板会动 | 通过。换一份质心右移的面板后，像素质心右移 > 20 px |
| S3 输入校验 | 通过。关节号 ≥ 256、长度不匹配、索引越界、空面板、257 面板、未写面板即渲染、面板只 1 关节却引用第 5 号——七种都报错，最后两种走 palette 长度那条 |
| S4 静态与蒙皮同帧 | 通过。静态红、蒙皮蓝，两种前后关系下中心像素分别取到蓝/红，说明描画顺序按先静态后蒙皮而非提交顺序；同帧 `draw_calls=2`、`instances=1`、`skinned_draws=1`；每帧换面板、连跑 10 帧 `created_buffers/textures/bind_groups` 全为 0 |

基准加两轴：`skindraw`（快照路径 `render_skinned_views`，n = 1/16/64）、`skin`（持久蒙皮，同一 n）。n 个实例各占屏幕一格、各用自己的面板（第一版写错成所有骨架共用 0 号面板，读数覆盖率 1.3%/0.0%，已修）。

本机读数（llvmpipe，中位数，ms/帧；覆盖率为非背景像素占比）：

| 场景 | n=1 | n=16 | n=64 | 覆盖率 1/16/64 |
|---|---|---|---|---|
| skindraw / 966×544 | 10.1 | 7.3 | 11.8 | 86.5 / 80.5 / 83.1 % |
| skin / 966×544 | 7.4 | 7.7 | 9.2 | 86.5 / 80.5 / 83.1 % |
| skindraw / 1920×1080 | 42.1 | 48.7 | 53.4 | 86.5 / 80.2 / 83.1 % |
| skin / 1920×1080 | 28.9 | 28.8 | 35.8 | 86.5 / 80.2 / 83.1 % |

读法：两轴覆盖率对齐说明画的确实是同一批像素；`skin` 相对 `skindraw` 便宜约两成（544p 64 个：9.2 对 11.8），边际成本约 22–31 µs/骨架——主要是每帧每骨架一次 16KB uniform 写加一次 bind group 切换。64 个 NPC 光蒙皮就要 9 ms，是本机最贵的一档，大半仍是软件光栅化在吃 CPU（同 1a 的结论）。真卡上已重测：优势更大而不是更小，见"真卡复核"。跨轮波动两成多的问题同样存在，个位数百分点不构成结论。

**没做**：窗口与交换链（步 2）、把真实帧时间喂给 `RenderSystem` 的自适应调速；蒙皮只支持 4 关节权重、无混合，半透明蒙皮物件仍走快照路径。

## 真卡复核（2026-11-25）

上面三份落地清单里所有"真卡未测"从此不成立。在一台真实的双显卡笔记本上（独显为 NVIDIA GeForce GTX 1650 Ti，4GB；Windows 11，Vulkan 与 DX12 两种后端）重跑了七轴基准（同一档位三次）、持久路径 20 条测试、蒙皮 GPU 测试与整机默认测试。按本 RFC 的口径**只记结论，不记毫秒数**；读数与复现命令在内部基线里。

| 悬空问题 | 真卡上的答案 |
|---|---|
| 1a 的数量级目标 | **成立**。持久路径的整帧时间与实例数无关（1 → 2048 实例的变化落在跨轮噪声里），每实例边际量不出来；同一台机器上快照路径的每实例边际仍然在。开发机上"只到 3–6 倍"是因为软件光栅化把顶点变换算进了每实例成本，那部分在真卡上不存在 |
| 同步回读占多少 | **是大头**。只提交不回读的 `psubmit` 与 `persist` 相差一个数量级以上——`persist` 九成以上的时间在等 GPU 完成并把像素拷回 CPU。风险 1 的后半句成立，前半句（成本在 CPU 侧）也成立 |
| 1b 值不值 | **就"拿到一帧像素要多久"而言，不值**。流水回读 `pasync` 与同步回读 `persist` 在噪声内，1080p 还略高。这与开发机的结论相同，但原因不再是软件光栅化：回读是一次串行的 CPU↔GPU 传输，流水重叠不掉它。保留 1b 的理由只剩结构上的——回读期间 CPU 不被阻塞、可以多帧在途。窗口用的呈现路径不回读，那才是帧时间的决定项，属步 2 |
| 1c 蒙皮 | 优势比开发机上**更大**：64 个蒙皮实例，持久路径相对快照路径省下的时间从"约两成"变成"三成半到五成半"。蒙皮的每实例边际在真卡上仍与分辨率有关，说明它含真实的光栅化成本，不只是每骨架的上传与绑定组切换 |
| 逐像素等价 | 真驱动下**差异像素仍为 0**（快照对持久、快照蒙皮对持久蒙皮）；持久路径 20 条、蒙皮 GPU 3 条、整机默认测试在 Windows 上全部通过 |
| 1080p 2048 实例 | 含同步回读在内落在 16.6 ms 预算内（约占三成）；544p 约占一成。注意这是回读口径的上界，不是呈现路径的帧时间 |

两条与硬件有关、此前不知道的事实：

- **双显卡机器上默认选到集成显卡。** Windows 上不指定适配器时，wgpu 按默认电源偏好选，落在集成显卡；同一条持久路径在核显上 1080p / 2048 实例**超出** 16.6 ms 预算。引擎目前没有"要独显"的表达。这直接决定步 2（窗口与交换链）怎么选适配器，列入开放问题第 4 条。
- **旧版核显驱动走 Vulkan 会在 wgpu-hal 初始化阶段崩溃**（访问冲突，任何读数之前），同一块卡走 DX12 正常。与 `gpu.rs` 里已记录的"MinGW 下 DX12/Vulkan 适配器枚举崩溃"是同一类问题：后端不是可以随便选的默认值。

复核顺带修了基准的一个错：`gpu_frame` 的适配器标签在 `WGPU_BACKEND=dx12` / `metal` / `all` 下会回落到默认实例，标出一个并不是被测对象的适配器——"报数必须带适配器名"这条纪律被它悄悄破坏了，此前只用过 `gl` 与 `vulkan` 所以没暴露。现在取值表与 `gpu.rs` 对齐，并额外打印被测渲染器自报的适配器，两边不一致时读数上看得出来。

仍未覆盖：窗口呈现路径与交换链（步 2）、更高端的独显与桌面卡、Linux 上的真卡、移动端。

## 背景

`render-wgpu` feature 下现有的场景渲染入口 `HeadlessRenderer::render_scene_views(&self, parts: &[ScenePart], camera) -> Result<RenderedImage, _>` 是按"渲染一张快照"设计的。读它的实现（`crates/oriera-render/src/gpu.rs`）可以看到每调用一次发生什么：

**每个绘制单元（part）：**

1. 把顶点在 CPU 上重新打包成 14 个浮点（位置 3 + 法线 3 + UV 2 + 颜色因子 4 + 金属度/粗糙度 2，56 字节）；
2. `create_buffer_init` 新建顶点缓冲；
3. `create_buffer_init` 新建索引缓冲；
4. `create_bind_group` 新建纹理绑定组；
5. 提交一次 `draw_indexed`，实例数恒为 1。

**每次调用：**

6. 新建相机 uniform 缓冲与绑定组；
7. 新建颜色纹理与深度纹理（尺寸取自相机）；
8. 渲染结束后 `copy_texture_to_buffer` → `map_async` → `device.poll(Wait)`，**阻塞到 GPU 完成**，再逐行拷贝进 `Vec<u8>`。

还有两点不是"开销"而是"能力"问题：

- **`ScenePart` 的坐标是世界坐标，没有模型矩阵。** 顶点着色器只接收 MVP，不接收模型变换。一个物件要移动，只能把它的全部顶点在 CPU 上变换后重新上传。
- **材质因子烘在顶点里。** 同一个网格换一种颜色就是另一份顶点数据，无法共用。

这套设计对它当初的目标（离线出图、测试断言像素）是合适的：一次调用拿到一张确定的图，没有需要管理生命周期的资源。但要让它进入帧循环——比如一个有上千静态物件和若干移动 NPC 的低多边形场景——它同时不满足三件事：资源不跨帧复用、物件不能带变换、每帧强制与 GPU 同步。

渲染层的帧成本基准 `crates/oriera-render/benches/gpu_frame.rs` 已落地，复现命令：

```sh
WGPU_BACKEND=gl EGL_PLATFORM=surfaceless \
  cargo bench -p oriera-render --features render-wgpu --bench gpu_frame -- --nocapture breakdown
```

它把"绘制数"（`draw/n`）与"填充率"（`fill/n`）分成两根轴。基准揭示的结构性事实是：**每个绘制单元的边际成本与分辨率无关**，即它不在光栅化里，而在上面第 1–5 步的 CPU 侧工作中。具体读数依赖适配器，不在本 RFC 里给；评审时请各自在自己机器上跑。

本 RFC 起草时没有任何真 GPU 上的读数，开发机只有软件光栅化，依据只有代码结构和"与分辨率无关"这个定性结论。同日补了真卡复核（见前面的落地清单之后），结论与之吻合；本 RFC 正文仍然不引用毫秒数——具体读数依赖适配器，换一块卡就变。

## 提案

### 1. 资源由调用方持有，上传一次，跨帧复用

沿用 `GpuTexture` 已有的惯例——"调用方持有值即持有资源"——新增两个同款类型：

| 类型 | 内容 | 创建入口 |
|---|---|---|
| `GpuMesh` | 顶点缓冲（位置 3 + 法线 3 + UV 2，32 字节）、索引缓冲、索引数、单调递增 `id` | `renderer.upload_mesh(positions, normals, uvs, indices)` |
| `GpuMaterial` | 材质 uniform（baseColor 因子、金属度、粗糙度）+ 纹理绑定组、单调递增 `id` | `renderer.create_material(factors, base_texture, mr_texture)` |

引擎**不做**隐式缓存：不按指针或内容哈希替调用方决定"这份顶点数据和上一次一样，可以复用"。数据变了而缓存不知道，是这类设计最常见的静默错误来源。复不复用由调用方显式表达。

### 2. 绘制列表带模型矩阵，同网格同材质走实例化

```rust,ignore
pub struct Instance<'a> {
    pub mesh: &'a GpuMesh,
    pub material: &'a GpuMaterial,
    pub model: [[f32; 4]; 4],
}

pub struct DrawList<'a> {
    pub instances: Vec<Instance<'a>>,
}
```

渲染一帧时，按 `(mesh.id, material.id)` 稳定排序，把连续相同的实例归成一段，每段一次 `draw_indexed`，实例数 = 段长。模型矩阵写进一个**持久**的实例缓冲（顶点步进模式为"每实例"），每帧用 `queue.write_buffer` 覆盖写入，不分配。

这需要一条新的顶点着色路径：顶点输入去掉颜色因子与 MR 因子，改为从材质 uniform 读取；位置先乘模型矩阵再乘 MVP。**片元着色器不变。** 现有 `pipeline_view_pbr` 与 `tex_bgl` 原样保留，新管线用独立的绑定组布局。

实例缓冲的容量显式管理：`DrawList` 超出容量时，由调用方调 `reserve` 扩容，引擎不在帧内悄悄重建。

### 3. 渲染目标持久，回读变成显式动作

| 类型 / 入口 | 说明 |
|---|---|
| `RenderTarget` | 颜色 + 深度纹理，`renderer.create_target(width, height)` 创建一次 |
| `RenderTarget::resize` | 显式调用才重建；之后第一帧清屏 |
| `render_draw_list(&DrawList, &Camera, &RenderTarget) -> FrameStats` | 提交命令后**立即返回**，不等待 GPU，不返回像素 |
| `read_target(&RenderTarget) -> Result<RenderedImage, _>` | 独立方法。需要像素的调用方（测试、离线出图）自己调 |

`FrameStats` 自报本帧的 `draw_calls`、`instances`，以及渲染器内部新建的缓冲 / 绑定组 / 纹理个数。最后三个数是为了让"稳态零分配"可被测试断言，而不是口头承诺。

### 4. 帧循环的位置不变

`ARCHITECTURE.md` 的规则是应用壳（`platforms/*`）持有 `World`，L2 调度器每帧把 `&mut World` 显式传给各 System，禁止跨层共享可变全局状态。本 RFC 不改这一点：**L5 不持有 `World`，也不自己遍历组件。** `DrawList` 由壳层（或一个显式拿到 `&World` 的 System）从世界状态构造，再交给渲染器。

`RenderSystem` 当前用可见 `Position` 计数充当渲染图占位，这个默认行为在本 RFC 下**不变**。把真实帧时间喂给 `Quality` / `observe_frame` 的自适应调速是好主意，但它会改一个已有的公开行为，另案处理。

### 5. 分步

| 步 | 内容 | 评审 |
|---|---|---|
| 1a | 第 1–3 节：资源类型 + 实例化管线 + 持久目标 + 显式回读；等价测试；基准加 `persist/draw/n` 轴 | 本 RFC |
| 1b | 回读的异步版本（不阻塞提交后续帧） | 实现前看 1a 的数据决定是否需要。**已落地**（见落地清单）：1a 没有真卡数据，这个条件实际没有满足，由项目所有者指示继续 |
| 1c | 蒙皮网格的持久路径（独立 `SkinnedDrawList`，每骨架一份关节 uniform） | 原定范围外。**已落地**（见落地清单）：项目所有者指示先做不需要真卡的部分 |
| 2 | 窗口与交换链：壳层提供窗口句柄，引擎据此创建 surface，把每帧的 swapchain 视图当作渲染目标 | **不在本 RFC 批准范围**，需单独评审 |

第 2 步单独评审的理由：它涉及"新平台"（GOVERNANCE 决策表里明确要开 RFC 的一档），而且引擎要不要为窗口引入依赖、surface 的创建方式在 wgpu 各版本间差异较大，都需要在动手前核对当前锁定版本的实际接口。本 RFC 对第 2 步只承诺一件事：第 3 节的入口接收 `RenderTarget`，因此交换链的帧视图可以不加区分地接进来。

### 6. 蒙皮路径不在本 RFC 内

`render_skinned_views`（bind 空间顶点 + 关节面板）是 NPC 角色要走的路。它的模型变换已经预乘进关节面板，所以物件移动要重传顶点的问题在它那里不存在，但每帧重建缓冲与绑定组的问题同样存在。

原稿把这条划在范围外，理由是每实例一份关节面板、涉及 uniform 容量上限（`MAX_JOINTS = 256`）。**这一步已落地**（步 1c，见落地清单）：做法不是实例化，而是一个骨架一份 16KB uniform + 每帧 `update_skeleton`，实例只引用骨架——共用同一骨架的多个实例会同步改姿势，这是有意的取舍，换来的是不必给每个实例单独拷贝面板。

## 可测断言（RFC 必附，否则不评审）

| 编号 | 断言 | 怎么测 |
|---|---|---|
| A1 | 新路径与 `render_scene_views` 像素等价 | 同一网格、单位模型矩阵、同一材质，两条路径各渲染一张；差异像素占比 ≤ 0.1%，且差异像素单通道差 ≤ 1/255。容差来自"材质因子从顶点插值改为 uniform"带来的浮点差异，预期实际为 0 |
| A2 | 稳态帧内不新建 GPU 资源 | 预热 3 帧后连续渲染 100 帧，`FrameStats` 自报的新建缓冲 / 绑定组 / 纹理计数全为 0 |
| A3 | 实例化生效 | 一个网格一个材质、N 个实例，`FrameStats.draw_calls == 1` 且 `instances == N`；两个材质时 `draw_calls == 2` |
| A4 | `render_draw_list` 不同步等待 | 该入口不返回像素、内部不调用 `device.poll(Wait)`——由代码结构保证，并以"调用后立即再次调用 `render_draw_list` 不抛错、`read_target` 才触发等待"做行为测试 |
| A5 | 现有行为不变 | `oriera-render --features render-wgpu` 现有 18 条测试与 3 条 ignored 不变；默认 feature 下不编译新代码；工作区 clippy `-D warnings` 零告警 |
| A6 | 基准可对照 | `gpu_frame` 基准新增 `persist/draw/n` 轴，与 `draw/n` 同网格、同分辨率、同覆盖率 |

性能目标：`persist/draw/n` 轴的每实例边际成本应比 `draw/n` 轴的每绘制单元边际成本低**一个数量级以上**。这一条在软件光栅化上就可以验证，因为被消除的成本本来就在 CPU 侧——但它是**目标，不是已测结果**。落地时如果达不到，在落地文档里如实写差多少，不调基准让它过。

## 替代方案

**不做新路径，直接在现有接口上接窗口。** 最省事，但接上去的就是每帧上千次缓冲分配加一次强制同步的路径，之后所有优化都建立在这上面。否决。

**在现有接口内部加缓存**：按顶点数据指针或内容哈希自动复用缓冲，调用方无感。表面上看改动最小，但失效策略是隐式的——调用方改了顶点数据、或释放再分配到同一地址，缓存都会给出错误结果，而且错得无声。否决，理由同第 1 节。

**让 `RenderSystem` 直接从 `World` 取网格与变换组件，做成真正的渲染图。** 这是 ARCHITECTURE 里写的目标形态（`BuildFrameGraph` / `AddPass`），也是长期正确的方向。但渲染图需要先有"GPU 资源"这个概念，而现在没有。本 RFC 的资源模型是它的前置，不是替代；先把资源与实例化做出来，渲染图才有东西可调度。

**在 wgpu 之上引入现成渲染器。** 能立刻拿到窗口、场景遍历、材质系统，代价是给 L5 引入一个体量很大的依赖，并且 L5 的分层边界（只依赖 L2/L3）要重新谈。与"引擎内核自己掌握帧提交"的定位冲突。否决。

## 影响面

- **层**：仅 L5，`crates/oriera-render`，全部在 `render-wgpu` feature 内。
- **契约**：无 schema 新增或修改。`contracts/` 下渲染相关的只有泼溅的 `oriera.render.splat.v1`，本 RFC 不碰 `oriera-splat`（它只消费相机）。
- **公开面**：新增 `GpuMesh`、`GpuMaterial`、`Instance`、`DrawList`、`RenderTarget`、`FrameStats`，以及 `HeadlessRenderer` 上的 `upload_mesh` / `create_material` / `create_target` / `render_draw_list` / `read_target`。移除或修改：无。
- **依赖**：步 1 不新增任何 crate 依赖。步 2 可能需要窗口相关依赖，届时单独评审。
- **文档**：落地后 `ARCHITECTURE.md` L5 节与 `STABILITY.md` 已知不稳定边界各加一条；`WASM-RENDERER.md` 描述的浏览器端渲染路径不受影响。
- **浏览器端**：JS 侧的 kernel.js / three.js 渲染器是独立路径，不共享代码，无影响。

## 兼容性

非破坏。现有 `render_scene_views`、`render_skinned_views`、`render_mesh*` 五个入口签名与行为冻结不变，测试与示例继续使用它们。默认 feature 下整个新路径不编译。

迁移是纯增量的：需要进入帧循环的调用方改用新入口；只需要一张图的调用方不用动。

## 风险

1. **没有真 GPU 读数，优化方向可能押错。** "成本在 CPU 侧"有分辨率无关这条证据支撑，但第 8 步的同步等待在真卡上占多大比重完全未测——它可能才是大头。缓解：A1–A6 不依赖真卡即可验证正确性；1a 落地后先在真卡上重跑基准，再决定 1b（异步回读）做不做。**已收敛**（见"真卡复核"）：两半都成立——成本确实在 CPU 侧，同步等待确实是大头。但"再决定 1b 做不做"这一步实际上没有等到数据，1b 是先落地后补测的，补测结论是它不降低单帧时间。
2. **wgpu 接口漂移。** 锁定的是 wgpu 30，其 `InstanceDescriptor` 已无 `Default`、适配器查询返回 `Result`，与旧版资料不一致。缓解：实现只对照锁定版本的实际接口，不照搬网上示例；升级 wgpu 时新路径与旧路径一起过测试。
3. **实例排序成为新的每帧成本。** 上千实例排序是 n log n，量级上可忽略，但排序会打乱调用方给的绘制顺序。透明物件依赖绘制顺序，而当前管线不处理透明。缓解：文档写明新路径只保证不透明物件的正确性；透明排序留到有透明需求时处理。
4. **自报计数不是硬约束。** A2 依赖渲染器内部如实计数，新增代码路径若忘了计数，断言就成了空话。缓解：计数集中在一处封装的创建辅助函数里，评审时检查没有绕过它的直接 `create_*` 调用。
5. **两条管线长期并存的一致性。** 片元着色器相同、顶点路径不同，今后改着色器时可能只改一边。缓解：片元着色器源码两边共用同一常量，A1 的等价测试长期保留。

## 开放问题（请在评论里答）

1. **资源所有权**：调用方持有 `GpuMesh` / `GpuMaterial`（本 RFC 的提议，与 `GpuTexture` 一致），还是渲染器发句柄并提供淘汰？后者省心，但要定义"什么时候可以淘汰"，而渲染器并不知道调用方还要不要用。
2. **蒙皮 NPC 要不要提前**（已按先做执行，问题转为够不够）：步 1c 已落地，本机 64 个蒙皮实例 544p 9.2 ms。若演示里 NPC 数量再多一个量级，每骨架一份 uniform 的模式会撞上 bind group 切换与上传次数，届时要么合并到实例化（每实例面板塞进 storage buffer），要么降 NPC 数。请确认首个演示的 NPC 上限。
3. **流程适用性**：按 `GOVERNANCE.md` 决策表，1a 是"L5 内新增 feature，不跨层、不动契约"，属于"PR + issue 讨论，1 人 approve"一档。本 RFC 走完整流程的理由是要一次定下公开面与所有权模型，且后续第 2 步确属"新平台"。是否把 1a 按快车道处理、只对第 2 步走完整 RFC，请明确。
4. **真卡基线**：原问"谁能提供一台有 `/dev/dri` 的机器"——已在 Windows 真卡上补测（见"真卡复核"），Linux 真卡仍缺。由此带出一个新问题：**适配器选择归谁**。双显卡机器上默认会选到集成显卡，持久路径在核显上 1080p 超预算；引擎是用"要高性能适配器"的电源偏好，还是由壳层在创建渲染器时显式指定？后者多一个参数，但步 2 的窗口恰恰是壳层才知道该画到哪块卡上。请在评论里表态。
5. **`RenderSystem` 的自适应调速**是否接真实帧时间——另案还是并入 1b？
