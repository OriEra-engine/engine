# RFC 0005 — 窗口与交换链：把持久渲染路径接到屏幕上

- 状态 / Status: **评论期中（2026-11-27 → 2026-12-04）**；实现排在 #207 合入之后
- 作者 / Author: 陈允文（@leslie520-bye）
- 影响契约 / Contract: 不动任何现有契约；`oriera.pal.gfx.v1` 不动
- 性质 / Nature: 新增能力（窗口呈现），非破坏；全部放在默认关闭的 feature 后面
- 影响层 / Layers: L5 `oriera-render`（新增 feature）；应用壳 `platforms/pc`（新增可选 bin）。L1 PAL、L2–L4、L6+ 不动
- 关联 / See also: RFC 0004（渲染持久路径，#207）、`docs/ARCHITECTURE.md`（L5 与应用壳）、`docs/STABILITY.md`、`crates/oriera-pal/src/gfx.rs`（`GfxBackend`）

---

## 0. 一页摘要

RFC 0004 把渲染内核改成了持久路径，但目前只能画到离屏纹理再回读，没有任何办法把画面显示出来。本 RFC 提议补上这一段：

1. **窗口归壳层，引擎不引入窗口库。** 壳层用任意窗口库开窗，把窗口句柄交给引擎。
2. **引擎新增一个带窗口的渲染器**，负责创建交换链、取帧、呈现。构造时必须显式给出后端和显卡。
3. **渲染入口新增一种借用型的"帧目标"**，只借用一张颜色视图和一张深度视图。交换链的一帧就是以这种形式接进来的。
4. **现有无头路径一行行为都不变。** `HeadlessRenderer::new()` 和现有渲染入口保持原样。

实现必须排在 #207 合入之后。

## 1. 背景

### 1.1 现状

- PC 壳 `platforms/pc` 没有窗口、没有事件循环、不依赖 wgpu。它跑 10 帧后打印一份报告就退出，渲染用的是统计式的 `RenderSystem`。
- 持久渲染路径（#207）的 `HeadlessRenderer` 把画面画进自己持有的 `RenderTarget`，然后回读成图像。所有已公开的读数都是回读口径，**窗口呈现这条路从来没有测过**。
- 仓库里没有窗口库。

### 1.2 RFC 0004 对第 2 步的承诺，对着代码不成立

RFC 0004 把窗口呈现划到第 2 步单独评审，并写了这样一句：第 2 步"只承诺一件事：第 3 节的入口接收 `RenderTarget`，因此交换链的帧视图可以不加区分地接进来"。

起草本稿时对着代码核对了这一句，结论是它不成立：

| | `RenderTarget`（现有） | 交换链的一帧 |
|---|---|---|
| 颜色 | 自己持有一张 `wgpu::Texture` | 只给一个 `TextureView`，所有权在交换链 |
| 深度 | 自己持有一张 `Depth32Float` 纹理 | 没有 |
| 格式 | 管线写死 `Bgra8Unorm` | 由交换链能力决定，不保证是它 |
| 尺寸 | 创建时定死 | 跟着窗口变 |

所以交换链的帧不能直接塞进 `render_frame`。本 RFC 提议新增一种帧目标来接它。RFC 0004 的这句话已随 #207 更正，见 #209 的勘误评论。

### 1.3 为什么要现在做

- 训练闭环走无头回读，不需要窗口。但调参、搭场景、给人演示都需要看到画面，现在只能出静态图。
- RFC 0004 的收益只在回读口径下验证过。呈现口径下每帧多一次取帧和一次呈现，结论是否还成立是未知数。
- 帧循环里"取帧 → 画 → 呈现"这一段如果一直空着，后面的事件、输入、自适应调速都没有落点。

## 2. 目标与非目标

**目标**

- 在真机上开一个窗口，用持久渲染路径把画面显示出来；固定尺寸下连续运行，GPU 资源不随帧数增长。
- 把"后端和显卡由壳层显式指定"这条已定处置落实到新入口上。
- 窗口尺寸变化、最小化、交换链失效这三种情况有明确行为，不 panic。
- 给出呈现口径下的测量方法，替换掉"回读口径"这一个唯一口径。

**非目标（本 RFC 不做）**

- 输入事件进世界。PAL 的 `input.rs` 已有契约，接线另案。
- 从 `World` 自动构造 `DrawList`。本 RFC 的窗口示例手工构造绘制列表。
- Pass 图、多窗口、HDR 与色彩管理、自动故障恢复。
- 浏览器端。three.js 是独立路径，不受影响。
- 实现 PAL `GfxBackend` 的 wgpu 版本。理由见 7.2。

## 3. 提案

### 3.1 分工

| 事情 | 归谁 | 理由 |
|---|---|---|
| 开窗、事件循环、高 DPI 换算 | 壳层 | 引擎不该为了开窗引入一整套窗口库 |
| 交换链、取帧、呈现、深度缓冲 | L5 `oriera-render` | wgpu 目前只在这一层使用，surface 是 wgpu 的对象 |
| 帧循环的驱动顺序 | 壳层 | 架构规定壳层持有 `World` 并驱动 L2 调度器 |
| 设备丢失后的重建 | 壳层 | 首版渲染器直接报错，不做自动恢复 |

窗口库的选型是壳层的事，本 RFC 不替壳层定。候选是实现 raw-window-handle 0.6 的库（wgpu 30 已 re-export 为 `wgpu::rwh`，锁定版本是 0.6.2）。具体版本在动手前核对。

### 3.2 帧目标 `FrameTarget`

新增一个只借用的类型：

```rust
pub struct FrameTarget<'a> {
    pub color: &'a wgpu::TextureView,
    pub depth: &'a wgpu::TextureView,
    pub width: u32,
    pub height: u32,
    pub format: wgpu::TextureFormat,
}
```

- 渲染入口新增 `render_frame_to(&DrawList, &SkinnedDrawList, camera, &FrameTarget)`。
- 现有 `render_frame(..., &RenderTarget)` 不删不改签名，内部改为用自己的两张视图拼一个 `FrameTarget`，再走同一个绘制函数。两条路径从此共用一份实现。
- 深度视图由调用方提供。无头路径用 `RenderTarget` 自带的；窗口路径用窗口渲染器持有的那张。

### 3.3 窗口渲染器 `WindowedRenderer`

新增一个类型，不复用 `HeadlessRenderer` 这个名字（它带窗口之后就不"无头"了）。两者共用同一份初始化和绘制代码。

**构造入口必带两个参数**：后端、显卡选择。这是 2026-11 已定的处置——引擎不内置"要高性能显卡"。

```rust
WindowedRenderer::new(
    options: WindowRendererOptions,          // 后端、显卡、呈现模式、帧延迟上限
    target: impl Into<SurfaceTarget<'window>>,
) -> Result<WindowedRenderer<'window>, WindowRendererError>
```

显卡选择支持两种：按枚举序号、按名称子串（必须唯一命中，命中多个报错）。引擎另提供 `enumerate_adapters(backends)`，方便壳层打印清单再选。

**创建顺序**（交换链必须先于选显卡创建，否则没法校验兼容性）：

```
instance → surface(窗口句柄) → 枚举显卡 → 按参数选一张
        → is_surface_supported 检查 → request_device
        → get_capabilities → configure
```

任何一步失败，错误信息里带上选中的显卡名和后端名。

现有 `HeadlessRenderer::new()` 的行为不变：仍然是默认后端、默认显卡。它在双显卡机器上会选到核显，这是已知行为，不在本 RFC 修改。

### 3.4 取帧结果怎么处理

wgpu 30 的 `get_current_texture()` 不返回 `Result`，而是返回一个七种状态的结果。处理规则先抽成一个纯函数，单测覆盖全部状态：

| 取帧结果 | 行为 |
|---|---|
| `Success` | 画，然后呈现 |
| `Suboptimal` | 画，然后呈现；返回值标记"需要重新配置"，壳层取当前窗口尺寸调 `resize` |
| `Outdated` | 不画。返回"需要调整尺寸"，壳层调 `resize` 后下一帧再画 |
| `Timeout` | 不画，本帧跳过 |
| `Occluded` | 不画（窗口被完全遮住），本帧跳过 |
| `Lost` | 不画。渲染器作废，后续调用直接报错，由壳层重建 |
| `Validation` | 报错 |

取到帧但没呈现时，那一帧在析构时自动释放，不需要特殊处理。

**世界是否照常推进由壳层决定。** 本 RFC 的窗口示例里，跳帧时世界照常推进，只是不画。

### 3.5 尺寸变化

- 壳层把窗口的物理像素尺寸交给 `resize(width, height)`，高 DPI 换算在壳层做。
- `resize` 重新配置交换链，并重建深度缓冲。尺寸没变则什么都不做。
- 宽或高为 0（最小化）时不配置交换链，只跳帧。
- 一帧以内不重复重建：同一尺寸连续多帧，纹理新建计数保持为 0。

### 3.6 帧循环

壳层的循环大致如下。调度器和 `World` 仍然由壳层持有，这一点不变。

```
loop {
    处理窗口事件（关闭 → 跳出；尺寸变化 → 记下新尺寸）
    如有新尺寸 → renderer.resize(w, h)
    sched.tick(&mut world)                  // 世界推进
    match renderer.begin_frame() {
        画 → renderer.render_frame_to(...); renderer.present(frame);
        跳过 / 需要调整尺寸 → 继续
        作废 / 出错 → 跳出
    }
}
```

### 3.7 呈现模式与帧延迟

- 默认 `Fifo`：垂直同步，不撕裂，所有平台都支持。
- 可选 `AutoNoVsync`：只用于测量，不是给玩家用的默认值。
- 帧延迟上限默认 2（wgpu 自己的默认值），可设为 1。它的含义是画面最多比世界状态晚几帧。对"人看着画面遥操作"的场景，2 帧是能感觉到的；对训练没有影响，因为训练走无头路径。取值见开放问题 3。

### 3.8 颜色格式

管线的颜色格式现在写死 `Bgra8Unorm`。交换链的格式从它支持列表里选：

- 列表里有 `Bgra8Unorm`：选它。
- 没有：构造失败，错误信息列出可用格式。

不在首版支持"按格式建管线"。这条限制写在文档和错误信息里，遇到时再按需求扩展。理由是多数桌面交换链都提供这个格式，先不为没见过的情况加分支。

## 5. 可测断言

无显示器环境下能跑的（进 CI）：

- **W1 视图入口等价。** 用普通纹理的视图构造 `FrameTarget` 并绘制，结果与 `RenderTarget` 路径逐像素一致。
- **W2 格式校验。** 帧目标的颜色格式不是 `Bgra8Unorm` 时报错，不提交任何命令。
- **W3 状态机全覆盖。** 七种取帧结果各自的决策有单测；跳过与出错时不调用呈现。
- **W4 现有行为不变。** `HeadlessRenderer::new()` 和现有渲染入口的测试、快照全部不动；默认 feature 下新代码不编译；clippy 与 fmt 干净。
- **W5 显式选择生效。** 按序号和按名称都能选中；名称命中多个时报错；交换链不被所选显卡支持时报错。

只能真机做的（手动，带显卡名和后端名记录）：

- **W6 窗口示例验收清单。** 能开窗；拖动改尺寸后画面正确；最小化再恢复不崩；关窗正常退出；日志打印实际使用的后端与显卡。
- **W7 稳态零新建。** 固定尺寸连续运行数分钟，纹理新建计数只在尺寸变化时非零。

## 6. 性能口径

以下是**目标，不是已测结果**。

- 1080p、不超过已验证过的实例规模（2048）时，每帧"提交 + 呈现"落在 16.6 ms 预算内，且不随实例数明显增长。
- 测量方法：`AutoNoVsync` 档下量 CPU 侧每帧耗时，同时用 GPU 时间戳量 GPU 侧耗时。`Fifo` 档下呈现会等垂直同步，CPU 侧帧时间被刷新率钳住，**不能**当作依据。
- 真卡绝对数字只进内部基线，公开只写相对预算的位置。沿用现有口径。

## 7. 替代方案

### 7.1 直接改现有快照接口来接窗口

已在 RFC 0004 否决，理由不变：每帧重建资源的成本在接口里，改不掉。

### 7.2 设备与交换链归 L1 PAL 的 `GfxBackend`

PAL 里已经有 `GfxBackend` 这个边界，`begin_frame` / `submit_frame` 的语义正好对应取帧和呈现。把 wgpu 实现放那里在架构上说得通。本 RFC 不选它，原因：

- PAL 目前零 wgpu 依赖，走这条路要让 L1 引入 wgpu，同时让 L5 接受外部传入的设备，改动面大得多。
- 目前只有一个实现者。按"有两个实现者再抽象"的惯例，现在抽象是为想象中的第二个平台付钱。
- 窗口渲染器的 `begin_frame` / `present` 与 `GfxBackend` 的两个方法一一对应，将来壳层写一个薄适配器就能实现该 trait，不需要返工引擎。

是否应该现在就做，见开放问题 2。

### 7.3 引入现成渲染器或框架

已在 RFC 0004 否决。

### 7.4 不做窗口

训练用无头路径已经够用；自研游戏如果用别的引擎做窗口，OriEra 自己也不需要。这条路成立的前提是"近期没有人需要在 OriEra 里看实时画面"。本 RFC 认为这个前提不成立（调参、搭场景、演示都需要），但这是判断，不是事实，所以列为开放问题 1。

## 10. 风险

1. **呈现口径没测过。** 取帧和呈现的成本、驱动的行为都是未知。2c 的第一件事就是量，量出来不达标要回来改本 RFC。
2. **交换链格式。** 如果目标机器的交换链不提供 `Bgra8Unorm`，首版直接失败。另外交换链可能给出 sRGB 变体，画面明暗与回读图是否一致，2c 时对照核对。
3. **驱动问题可能在窗口路径上以另一种形式出现。** 已知旧 Intel 驱动在无头初始化时走 Vulkan 会崩、走 DX12 正常。窗口路径未验证。"后端由壳层指定"这条处置正是为此保留的。
4. **帧延迟带来的观感。** 默认 2 帧延迟在遥操作时可能被感知到。
5. **依赖 #207。** #207 未合入前，2a 无法开始。

## 11. 开放问题

1. **窗口呈现是不是近期必需？** 见 7.4。
2. **设备与交换链归 L5（本提案）还是 L1？** 见 7.2。
3. **帧延迟上限取 1 还是 2？**
4. **交换链格式不匹配时，报错（本提案）还是按格式建管线？**
5. **壳层是否接受引入一个窗口库？** 引入哪个由壳层决定，但需要确认"引擎不引入、壳层引入"这个分工本身。
6. **窗口演示能带多少个 NPC？** 目前**没有测过**，本 RFC 不写数字。已知的约束是：蒙皮路径是"一个骨架一份 16 KB uniform、每帧更新一次"，单骨架上限 256 关节，没有做实例化。要支撑成百上千个同时活动的 NPC，需要把每实例数据搬进 storage buffer，这不在步 2 范围内。上限数据由 2c 在真机上量出来后回填。

## 13. 核对记录

**已对着源码核对的**

- wgpu 30.0.2 的 surface 接口：`create_surface`、`SurfaceTarget`、`get_default_config`、`configure`、`get_current_texture` 的七种结果、`Queue::present`、`Adapter::is_surface_supported`、`Instance::enumerate_adapters`。来源是本机 cargo registry 里的 wgpu 源码。
- `PresentMode` 的六个取值、`CompositeAlphaMode` 的五个取值、`SurfaceConfiguration` 的字段。
- `Surface`、`Device`、`Texture` 都是 `Send + Sync`（源码里有静态断言）。线程模型因此不构成约束。
- 仓库现状：`RenderTarget` 的字段、管线颜色格式、`HeadlessRenderer::new` 的实现、PC 壳的循环、PAL 的 `GfxBackend` 与依赖。

**没有核对、动手前要查的**

- 窗口库版本与 raw-window-handle 0.6 的匹配。
- 目标机器上交换链实际提供的格式列表。
- 着色器输出的色彩处理接到交换链后是否仍然正确。
